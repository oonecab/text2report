# 权限与组织

## 问题一：组织权限的校验时机与 LLM 忽视 Prompt 限制的处理

### 问题
用户 A 属于华北区，他提问"全国毛利汇总"，系统会怎么处理？组织权限是在 SQL 生成之前裁剪还是生成之后校验？如果 LLM 忽视了 Prompt 里的组织限制，生成了跨组织的 SQL，你能拦住吗？

### 答案

**两层保护：Prompt 提示 + 代码校验，但 SqlGuardService 拦不住跨组织 SQL。**

---

## 用户 A 问"全国毛利汇总"的完整处理流程

### 假设条件
- 用户 A 属于**华北区**（orgId = 5）
- 用户 A 的权限范围：华北区及其下级部门（orgIds: 5, 51, 52, 53）
- 用户请求查询**全国**（orgId = 1）

### 第一层保护：权限校验（SQL 生成之前）

```java
// OrchestratorService.initializeContext()
List<Integer> accessibleOrgIds = userService.resolveAccessibleOrgIds(queryContext.getUserId());
// accessibleOrgIds = [5, 51, 52, 53]  ← 用户 A 只能看这些

if (!accessibleOrgIds.contains(queryContext.getOrgId())) {
    // 用户请求 orgId=1（全国），但用户没有全国权限
    throw new BusinessException(ErrorCode.FORBIDDEN, "您没有该组织的查询权限");
}
```

**结果：请求被拒绝，用户看到"您没有该组织的查询权限"。**

---

## 如果 LLM 无视 Prompt 里的 org 限制？

假设用户请求自己权限范围内的组织（orgId = 5），但 LLM 生成了这样的 SQL：

```sql
-- 用户有权访问 org_id IN (5,51,52,53)
-- 但 LLM 生成了跨组织的 SQL
SELECT SUM(revenue - cost) AS total_profit
FROM fact_gross_profit_detail
WHERE org_id IN (1, 2, 3)  -- ← 用户无权访问的全国数据！
```

### SqlGuardService 能拦住吗？

**拦不住。**

SqlGuardService 的检查内容：

```java
// 检查项目：
if (statement instanceof Select) → validateSelect()
    ├── SELECT * 检查 ✅
    ├── 危险函数检查 ✅
    ├── 系统表访问检查 ✅
    ├── DELETE/UPDATE/INSERT 检查 ✅
    └── **没有 org_id 检查** ❌
```

**SqlGuardService 只检查 SQL 的"语法和语义安全"，不检查业务权限。**

---

## 实际执行链路

```
用户问 "全国毛利汇总"（但用户只有华北区权限）
    ↓
代码校验：accessibleOrgIds 不包含 orgId=1 → 拒绝
    ↓ （如果用户问的是自己有权限的 org）
Prompt 生成：WHERE org_id IN (5,51,52,53)
    ↓
LLM 生成 SQL
    ↓
SqlGuardService.validate() → 检查 AST
    ├── SELECT * ✅ 没 *
    ├── 危险函数 ✅ 没有
    ├── 系统表 ✅ 没有
    └── org_id 检查 ❌ 不检查
    ↓
QueryExecutorService.execute()
    ↓
如果 SQL 没有 org_id 过滤 → 执行，返回跨组织数据
```

---

## 数据库层面的最后保护

理论上可以加 PostgreSQL Row Security Policy（行级安全策略），但这不是 SqlGuardService 的职责。

---

## 总结

| 问题 | 答案 |
|------|------|
| 权限在校生成之前还是之后校验？ | **之前**——代码层面校验用户请求的 orgId 是否在 accessibleOrgIds 里 |
| LLM 无视 org 限制能拦住吗？ | **拦不住**——SqlGuardService 不检查 org_id 子句 |
| 最后怎么兜底？ | 依赖数据库行安全策略，或假设 LLM 会遵守 Prompt |

## 问题二：JWT 黑名单的 Redis 失效策略

### 问题
JWT 黑名单存 Redis，Redis 挂了怎么办？是直接放行（fail-open）还是全部拒绝（fail-closed）？

### 答案

**fail-open（放行）——代码里明确写的。**

---

## 代码证据

```java
/**
 * Check if token is blacklisted in Redis
 * Fix: P0-3
 */
private boolean isTokenBlacklisted(String token) {
    String blacklistKey = JwtConstants.BLACKLIST_PREFIX + token;
    try {
        return Boolean.TRUE.equals(stringRedisTemplate.hasKey(blacklistKey));
    } catch (Exception e) {
        // Redis unavailable - fail open, only validate signature
        log.warn("Redis blacklist check failed, proceeding without blacklist check: {}", e.getMessage());
        return false;  // ← 返回 false = "不是黑名单" = 放行
    }
}
```

---

## 实际行为

| Redis 状态 | 黑名单检查结果 | 行为 |
|-----------|--------------|------|
| Redis 正常 | token 在黑名单 → true | 拒绝登录 |
| Redis 正常 | token 不在黑名单 → false | 继续校验 JWT 签名 |
| **Redis 挂了** | **抛异常 → catch → return false** | **放行，只验 JWT 签名** |

---

## 为什么选择 fail-open？

### 安全 vs 可用性的权衡

| 策略 | 用户体验 | 安全风险 |
|------|---------|---------|
| fail-open（放行） | ✅ Redis 挂了服务仍可用 | ❌ 被拉黑的 token 还能用直到 TTL 过期 |
| fail-closed（拒绝） | ❌ Redis 挂了所有人都登录不了 | ✅ 安全：Redis 挂了 = 所有 token 失效 |

### 项目选择

代码注释已经写明了：
```java
// Redis unavailable - fail open, only validate signature
```

**选择可用性，牺牲短期安全性。**

---

## 影响分析

### 场景：用户登出后 Redis 恰好挂了

1. 用户点击"退出登录"
2. 系统把 token 加入 Redis 黑名单
3. **此时 Redis 恰好挂了** → 黑名单写入失败
4. 用户带着刚退出登录的 token 继续访问
5. 系统检查黑名单 → Redis 抛异常 → 放行
6. **用户用已注销的 token 还能访问**

### 缓解措施

```java
// Redis 黑名单 TTL 和 JWT TTL 一致
// 即使黑名单写入失败，token 最多再存活 24 小时
```

---

## 总结

| 问题 | 答案 |
|------|------|
| Redis 挂了怎么处理？ | **fail-open（放行）** |
| 为什么不 fail-closed？ | 代码注释写了"fail open, only validate signature"，是设计决策 |
| 安全影响？ | Redis 挂了期间，黑名单失效，已注销的 token 仍可用 |
| 缓解措施？ | JWT 本身有 24h TTL，窗口期有限 |

## 问题三：MANAGER 给 USER 分配权限的上界校验

### 问题
MANAGER 角色给下属 USER 分配权限，MANAGER 能不能给 USER 分配比自己更大的权限范围？代码里有没有做上界校验？

### 答案

**有 orgId 上界校验，但没有 scope 上界校验。MANAGER 可以给 USER 分配比自己更大的 scope。**

---

## 代码里的校验逻辑

```java
@Override
public void grantOrgAccess(UserOrgGrantRequest req, String operatorUsername) {
    SysUser operator = requireUserByUsername(operatorUsername);
    requireUserById(req.getUserId());

    if ("MANAGER".equalsIgnoreCase(operator.getRole())) {
        // 获取 MANAGER 自己能访问的 org 列表
        List<Integer> accessible = resolveAccessibleOrgIds(operator.getId());

        // 检查目标 org 是否在 MANAGER 的权限范围内
        if (!accessible.contains(req.getOrgId())) {
            throw new BusinessException(ErrorCode.FORBIDDEN, "权限范围外的组织不可授权");
        }
    }
    // ... 继续执行授权
}
```

---

## 有校验：orgId 上界

**MANAGER 只能给 USER 分配自己有权访问的 orgId。**

```
MANAGER 自己能访问：[5, 51, 52, 53]（华北区 + 3个下级部门）
    ↓
MANAGER 想给 USER 分配 orgId = 1（全国）
    ↓
accessible.contains(1) = false
    ↓
拒绝："权限范围外的组织不可授权"
```

---

## 但没有校验：scope 上界

**MANAGER 可以给 USER 分配比自己更大的 scope。**

### 场景演示

```
MANAGER 的权限：
    - grant on org=5 (华北区)，scope=CHILDREN
    - resolveAccessibleOrgIds() 返回：[5, 51, 52, 53]

MANAGER 尝试给 USER 分配：
    - orgId=5 (华北区)，scope=ALL  ← ← ← 问题在这里！
```

### 校验逻辑

```java
// 只检查了 orgId 是否在 accessible 里
if (!accessible.contains(req.getOrgId())) {  // 5 在 [5,51,52,53] 里 → 通过
    throw new BusinessException(...);
}
// 没有检查 scope 是否超出 MANAGER 的 scope 范围！
```

### 结果

| MANAGER 权限 | 给 USER 分配 | 结果 |
|-------------|-------------|------|
| org=5, scope=CHILDREN | org=5, scope=CHILDREN | ✅ 正常 |
| org=5, scope=CHILDREN | org=5, scope=ALL | ❌ **可以**（不应该可以） |
| org=5, scope=SELF | org=5, scope=CHILDREN | ❌ **可以**（不应该可以） |

---

## 漏洞场景说明

```
安全漏洞示例：

MANAGER（张三）：
    权限范围：华北区 + 下属3个部门（scope=CHILDREN）
    可访问 org：[5, 51, 52, 53]

USER（李四）：

张三给李四分配：
    orgId=5（华北区）
    scope=ALL（整个子树）  ← ← 系统没检查这个！

结果：李四能看到 5,51,52,53 以外的组织数据
```

**代码检查了"你能看到哪些 org"，但没检查"你给别人的 scope 是否超过你自己的 scope"。**

---

## 总结

| 问题 | 答案 |
|------|------|
| 有上界校验吗？ | **有**——检查 orgId 是否在 MANAGER 的 accessibleOrgIds 里 |
| 校验严格吗？ | **不严格**——只检查 orgId，没检查 scope |
| MANAGER 能不能给 USER 分配比自己更大的 scope？ | **可以**——代码里没有 scope 上界校验 |
| 漏洞场景 | MANAGER 权限是 `org=5, scope=CHILDREN`，可以给 USER 分配 `org=5, scope=ALL` |
