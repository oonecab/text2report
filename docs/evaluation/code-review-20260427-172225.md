## 2. 架构设计

### 2.1 后端分层

```
controller → orchestrator → { metadata, llm, sql-guard, executor, audit }
                                 ↑
                            all services
```

**评价**：清晰的单向依赖，`OrchestratorService` 作为编排中心，各子服务职责单一。符合 SOLID 原则。

### 2.2 前端分层

```
pages → components → stores (zustand) → services (axios) → backend API
                              ↓
                        localStorage (auth persist)
```

**评价**：状态管理轻量且合理，组件拆分粒度合适。

### 2.3 数据流 (一次查询的完整链路)

```
用户输入 → QueryController → OrchestratorService
  → resolveOrgContext (JWT claims / sys_user_org)
  → auditService.logQueryStart (async upsert)
  → queryCacheService.getCachedResult (Redis check)
  → llmService.detectIntent (keyword-based)
  → orgService.resolveSubtreeIds (recursive CTE, Redis cached)
  → metadataService.retrieveForPrompt (vector + keyword hybrid RAG)
  → promptBuilder.buildSqlGenerationPrompt (template fill)
  → llmService.generateSQL (OpenAI/DeepSeek API via OkHttp)
  → sqlGuardService.validate (JSqlParser AST, blocked schemas/functions/*)
  → sqlGuardService.validateOrgScope (org_id filter verification)
  → queryExecutorService.execute (JDBC prepared statement, read-only pool)
  → queryExecutorService.enrichColumnMeta (label lookup from meta_column)
  → llmService.summarizeResults (ResultProfile only, Rule 1 compliance)
  → auditService.updateAuditLog (async upsert)
  → queryCacheService.cacheResult (Redis set, 1800s TTL)
  → ApiResult<QueryResultDTO> response
```

**评价**：链路完整，每步职责清晰，Rule 1 (LLM 不接触数据) 得到严格执行。

## 3. 后端逐模块评审

### 3.1 核心编排层

**文件**：`OrchestratorService.java`

**优点**：
- `buildQueryContext` → `initializeContext` → `executeWithRetries` → `buildResult` 的管道设计清晰
- 重试逻辑区分了"可重试错误"(column/table/syntax error)和"不可重试错误"(guard blocked/permission denied)
- 置信度计算 `resolveConfidence` 和 `applyConfidence` 为两套逻辑(基于元数据 vs 基于重试次数)，提示可能存在重复设计的意图
- `ResultProfile` 传递给 `summarizeResults`，严格遵守 Rule 1

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| B1 | ⚠️ 中 | `executeWithRetries()` 和 `validateOrRepair()` 都使用 `while(true)` 无限循环。虽然有 maxRetries 检查，但如果 `isRetryable()` 判断失误(始终返回 true)，将导致无限循环。建议添加硬上限保护(如 `while (true) { if (retries >= 3) throw ... }`) |
| B2 | ⚠️ 中 | `OrchestratorService` 有两个构造函数——一个用于生产(@Autowired)，一个用于测试(backward-compatible)。生产构造函数依赖 `UserService` 和 `SysUserOrgMapper`，但 `initializeContext()` 中通过 `userService != null` 做空安全检查。这种防御式写法暗示了不稳定的 DI，建议统一构造函数并在测试中使用 Mock |
| B3 | ℹ️ 低 | `applyConfidence` 与 `resolveConfidence` 逻辑重复——前者是硬编码值(0.90/0.75/0.60)，后者是基于元数据的动态计算。从调用链看 `applyConfidence` 在 retry 循环后调用，`resolveConfidence` 在 `buildResult` 中再次调用。逻辑可以合并 |
| B4 | ℹ️ 低 | `isRetryable()` 基于英文错误消息做字符串匹配 (`lower.contains("column")` 等)，但 `classifySqlError()` 在某些情况下返回中文消息(如 `"查询执行超时"`)。如果中文环境返回错误消息，重试判断将失效 |
| B5 | ℹ️ 低 | `sanitizeException()` 中硬编码检测 `"超时"` 来判断超时错误，与其他基于 `ErrorCode` 的判断风格不一致 |

### 3.2 SQL 安全层

**文件**：`SqlGuardService.java`

**优点**：
- 这是整个项目安全设计最亮眼的部分。使用 JSqlParser AST Visitor 模式遍历整个 SQL 树，而非基于正则的字符串匹配
- 覆盖范围全面：`SELECT *`、`t.*`、系统 schema (`pg_catalog`, `information_schema`)、危险函数 (`xp_cmdshell` 等)、所有 DML/DCL 操作
- `validateOrgScope` 通过 AST 递归检查 WHERE 条件是否包含合法的 `org_id` 过滤，支持 `=` 和 `IN (...)`
- LIMIT 自动注入是防御性编程的典范
- 代码注释记录了 P0-2 修复，体现了安全审计历史

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| B6 | ⚠️ 中 | `OrgScopedTableContext` 识别需要 org scope 的表时，规则是 `tableName.startsWith("fact_")` 或 `tableName ∈ ORG_SCOPED_TABLES`。如果新增其他需要 org 范围过滤的表(如新增某个维度表)，需要修改代码才能生效。建议将需要 org scope 的表配置化(如从 `meta_table` 的某字段读取) |
| B7 | ℹ️ 低 | `validateOrgScope` 检查 `org_id = ?` 时，`isOrgIdColumn` 只匹配列名精确等于 `"org_id"`(忽略大小写)。如果 SQL 使用了表别名(如 `d.org_id`)，JSqlParser 的 `Column.getColumnName()` 仍返回 `"org_id"`，正确处理。但如果是 `dim_org.org_id` 带 schema 前缀，情况相同——当前逻辑可以正确处理 |
| B8 | ℹ️ 低 | `BLOCKED_FUNCTIONS` 只包含 SQL Server 系统过程。对 PostgreSQL，还应考虑 `lo_import`、`lo_export`、`pg_read_file`、`pg_read_binary_file`、`pg_ls_dir` 等函数 |
| B9 | ℹ️ 低 | `BLOCKED_SCHEMAS` 包含 `sys`、`syscolumns`、`master`、`msdb`(SQL Server)在 PostgreSQL 环境中不会生效，但不影响安全性 |

### 3.3 LLM 集成层

**文件**：`LLMService.java`, `OpenAILLMService.java`, `LLMAsyncExecutor.java`, `PromptBuilder.java`

**优点**：
- 接口驱动设计(`LLMService` interface)，切换 LLM provider 只需配置变更
- `LLMAsyncExecutor` 作为独立 Bean 解决 `@Async` 自调用代理失效问题——这是一个成熟的设计决策
- `@ConditionalOnProperty` 区分 OpenAI/Local 实现，避免 Bean 冲突
- `cleanJsonContent()` 处理 LLM 常见的 markdown code block 包裹——实用的防御性处理
- `extractContent()` 有完善的回退链：`choices[0].message.content` → `root.content` → `rawResponse`
- `PromptBuilder` 支持文件系统和 classpath 双路径加载，并做 sanitize (API key 脱敏)
- `buildRequestBody` 强制 `response_format: { type: "json_object" }`

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| B10 | ⚠️ 中 | `detectIntent()` 是纯关键词匹配而非 LLM 语义理解。方法上有 TODO 注释表明开发者知道这个限制。但这意味着 intent 分类精度不高(如"哪个部门毛利最低"被归为 extreme 而非 ranking+extreme) |
| B11 | ⚠️ 中 | `recommendChartType()` 也是纯规则驱动(根据 column 数量和 rowCount)，而非 LLM 驱动。与文档 `api-contract.md` 的 `recommended_chart` 字段语义有差异——后端实际用的是规则，但文档可能暗示是 LLM 推荐 |
| B12 | ⚠️ 中 | `AuthService.generateTokenWithJti()` 和 `readSecretKey()` / `readExpirationMs()` 使用 **Java 反射** 调用 `JwtUtil` 的 private 方法和字段。这是危险的反模式——破坏了封装性，在 JDK 升级或 Security Manager 启用时会直接失败。应改为：`JwtUtil` 提供 package-private 或 public 的 `getSecretKey()` 方法，以及 `getExpirationMs()` 方法 |
| B13 | ℹ️ 低 | `LLMAsyncExecutor` 每次调用都创建新的 `OkHttpClient` 实例，与配置中声明的连接池和线程池不一致。建议复用 OkHttpClient 实例(或至少复用连接池) |
| B14 | ℹ️ 低 | `OpenAILLMService.buildSystemPrompt()` 硬编码中文 system prompt。应外置为 prompt 模板文件 |
| B15 | ℹ️ 低 | `callLLMSafely()` 通过 `CompletableFuture.join()` 阻塞，实际上把异步转成了同步。`@Async` 的线程池在这里的作用是隔离而非提升吞吐量——这个设计选择需要文档化 |

### 3.4 安全认证层

**文件**：`SecurityConfig.java`, `JwtAuthFilter.java`, `JwtUtil.java`, `AuthService.java`

**优点**：
- JWT + Redis Session 双验证模式——每次请求验证 token jti 是否与 Redis 中保存的当前 session 一致，实现了"单设备登录"
- `JwtUtil.validateSecret()` 在启动时检查密钥强度(长度≥32、字符种类≥8、无连续/重复模式)——企业级安全实践
- Rate limiting 使用 Redis Sorted Set 实现滑动窗口，而非简单的固定窗口计数器
- CORS 配置使用 `allowedOriginPatterns` 而非 `allowedOrigins`，支持通配符子域名
- URL 级别角色授权(`hasRole("ADMIN")`, `hasAnyRole("ADMIN", "MANAGER")`)

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| B16 | 🔴 高 | `AuthService.generateTokenWithJti()` 通过反射调用 `JwtUtil.getSecretKey()`(private method)。这是一种严重违反封装的设计。若未来升级 JDK 版本(如强封装模块)或启用 Security Manager，此代码将直接抛出 `InaccessibleObjectException`。应立即修复：将 `JwtUtil.getSecretKey()` 改为 package-private 或添加 `generateTokenWithJti` public 方法 |
| B17 | ⚠️ 中 | `SecurityConfig` 中 `authenticationEntryPoint` 和 `accessDeniedHandler` 使用 **手动拼接 JSON 字符串** 的方式构建错误响应，而非使用已注入的 `ObjectMapper`。如果将来响应格式变更，容易遗漏此处的字符串拼接 |
| B18 | ℹ️ 低 | `JwtAuthFilter.extractToken()` 用空字符串 `""` 作为"token 格式错误"的哨兵值，然后在上层用 `"".equals(token)` 判断。这种哨兵模式不直观，建议用 `Optional<String>` 或自定义 result 类型 |
| B19 | ℹ️ 低 | `AuthService.logout()` 在 token jti 匹配时才删除 Redis session，但如果 token 已过期(parseToken 返回 null)，`logout()` 静默不处理。这本身不是问题，但前端需要知道登出总应该成功 |

### 3.5 元数据与 RAG

**文件**：`MetadataService.java`, `EmbeddingService.java`

**优点**：
- 混合检索策略：向量相似度搜索 + 关键词回退(fallback-to-keyword)，兼顾语义理解和精确匹配
- 搜索词提取 `extractSearchTerms()` 包含中英文混合处理，覆盖了业务术语
- 表优先级排序：fact 表 > dim 表 > 其他
- `augmentAndPrioritizeTablesReferencedByExamples()` 从 SQL Example 中提取表名补充检索——这是 RAG 增强的好实践
- Embedding 异步存储(`@Async`)，不阻塞 CRUD 操作
- 元数据变更后自动失效查询缓存(`queryCacheService.invalidateAllQueryCache()`)

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| B20 | ⚠️ 中 | `extractTableNamesFromExamples()` 使用正则 `(?i)\b(?:from|join)\s+([a-zA-Z_][a-zA-Z0-9_]*)` 提取表名，这种方式对于复杂 SQL(子查询、CTE、别名)会误提取。例如 `FROM (SELECT ...) AS t` 会提取到 `SELECT` |
| B21 | ℹ️ 低 | `searchTablesByColumnTerms()` 的评分机制 `scoreColumnAgainstTerms` 中，如果 term 包含 column name 就给 5 分，反之也给 5 分(`normalizedTerm.contains(columnName)`)。对于短列名(如 `id`)，这会导致高误匹配 |
| B22 | ℹ️ 低 | `syncAll()` 方法是同步循环调用 embedding API，对于大量数据可能超时。虽然有 `@Async` 包装，但 `syncAll()` 本身在主线程执行 |

### 3.6 基础设施与配置

**文件**：`application.yml`, `BusinessDataSourceConfig.java`, `RedisConfig.java` 等

**优点**：
- `application.yml` 中所有敏感信息都通过 `${ENV_VAR:default}` 占位，无硬编码凭据
- 三数据源配置(business/meta/vector)各司其职
- HikariCP 连接池配置合理(read-only 在业务库强制开启)
- 配置项丰富且有条理

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| B23 | 🔴 高 | 原 `application.yml` 的 vector 数据源默认值曾包含真实数据库地址和密码。本报告已将原值脱敏；修复要求是将地址默认值改为本机地址，并将密码改为必填的 `${VECTOR_DB_PASSWORD}` |
| B24 | ⚠️ 中 | `BusinessDataSourceConfig` 的 `businessDataSource()` Bean 上标注了 `@Primary`，但没有显式设置 `read-only: true`（依赖 application.yml 中的 `hikari.read-only: true`）。如果在 Java 代码层面也显式设置，会更加防御性 |
| B25 | ℹ️ 低 | `RedisConfig` 没有配置连接池的阻塞等待行为 (`max-wait` 设为 -1ms 表示无限等待)。在高负载下可能导致线程池耗尽 |
| B26 | ℹ️ 低 | `PromptBuilder` 的文件系统回退尝试了三个相对路径(`prompts/`, `../prompts/`, `../../prompts/`)，这是因为不同启动方式(IDE vs jar)的工作目录不同。建议统一通过配置参数或环境变量解决，而非硬编码多路径试探 |

### 3.7 异常处理与 API 契约

**文件**：`GlobalExceptionHandler.java`, `ErrorCode.java`, `ApiResult.java`

**优点**：
- 统一异常处理，`@RestControllerAdvice` + 分级处理(BusinessException、Validation、Auth、Generic)
- `BusinessException` → HTTP Status 映射合理
- `ErrorCode` 分为 4001-4005(业务错误)和 5001(内部错误)，与 CLAUDE.md 规范一致
- `sanitizeException()` 对内部错误统一返回通用消息，防止信息泄露

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| B27 | ⚠️ 中 | `ErrorCode.LLM_ERROR` 的值是 `503002`，与文档定义的 4001-4005/5001 范围不一致。这会导致 `GlobalExceptionHandler` 的 HTTP status 映射逻辑中 `code >= 4001 && code <= 4005` 判断失效，LLM_ERROR 会落入 `else` 分支返回 200 OK，这是错误的 HTTP 状态码 |
| B28 | ℹ️ 低 | `GlobalExceptionHandler` 中 `handleBusinessException` 的 HTTP status 映射用了硬编码数字(401, 403, 404, 429)，与 `ErrorCode` 枚举中的值重复。建议通过 `ErrorCode` 增加 `httpStatus` 属性统一管理 |

## 4. 前端逐模块评审

### 4.1 状态管理与认证

**文件**：`useAuthStore.ts`, `useQueryStore.ts`, `useOrgStore.ts`

**优点**：
- Zustand 选择合理——比 Redux 轻量，比 Context 性能好
- `useAuthStore` 使用 `persist` 中间件持久化到 localStorage，配合 `partialize` 选择性持久化
- `isAdmin()` / `isManagerOrAbove()` 使用 getter 函数而非派生状态，避免了状态不一致

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| F1 | 🔴 高 | `useAuthStore` 使用 Zustand `persist` 中间件将 JWT token 存储在 `localStorage`。localStorage 对 XSS 攻击完全暴露——任何注入的脚本都可以读取 token。在 Demo 阶段可接受，但生产环境应使用 httpOnly cookie 或至少在 localStorage 中加密存储 |
| F2 | ⚠️ 中 | `useQueryStore.submitQuery` 的错误消息处理粗糙——直接取 `err.message`，没有根据 HTTP 状态码或业务错误码做分类处理。例如 401 应该触发重新登录，429 应该提示频率限制 |
| F3 | ℹ️ 低 | `useAuthStore.setAuth` 中 `userId` 赋值逻辑复杂：`user.userId ?? user.id`。如果两个字段都不存在，`userId` 为 null，这在类型系统上没有体现 |

### 4.2 路由与权限

**文件**：`routes.tsx`, `AuthGuard.tsx`

**优点**：
- 嵌套路由结构清晰：`AuthGuard → QueryLayout/AdminLayout → Pages`
- 两层权限控制：`AuthGuard(requireManager)` + 嵌套的 `AuthGuard(requireAdmin)`
- 精细的页面级权限隔离

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| F4 | ⚠️ 中 | `AuthGuard` 只在前端检查角色，后端 `SecurityConfig` 有 URL 级别的角色检查。但如果前后端权限配置不一致(如 admin 页面前端限制为 MANAGER，后端限制为 ADMIN)，会导致用户看到页面但 API 调用失败。建议将权限配置统一由后端 API 返回(如 `/auth/me` 返回 permissions 列表) |
| F5 | ℹ️ 低 | 路由配置中 admin 子页面 `/admin/datasources` 需要在 `requireAdmin` 的 AuthGuard 内访问，但 `DataSourceListPage` 的 API 调用可能也需要检查 |

### 4.3 API 层

**文件**：`request.ts`, `queryApi.ts`, 等

**优点**：
- Axios 拦截器设计合理——请求自动注入 `X-Request-ID` 和 Bearer token
- 响应拦截器检查标准 `ApiResponse` 格式并解包
- 401 响应自动清除 store 并跳转登录页
- `apiGet` / `apiPost` 等泛型辅助函数提供良好类型推断
- 120s 超时设置合理(LLM 调用可能较慢)

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| F6 | ⚠️ 中 | `showError` 的 fallback 路径使用动态 `import('antd')` 来调用 `message.error`。这是异步操作，如果页面已卸载，会导致内存泄漏或无意义的错误提示 |
| F7 | ⚠️ 中 | 响应拦截器的成功判断：`res.code === 'SUCCESS' \|\| res.code === 0 \|\| res.code === 200`。类型比较不一致——后端返回数字 code(如 200)，但这里同时检查字符串 `'SUCCESS'`。如果后端统一返回数字，字符串比较永远不会为真 |
| F8 | ℹ️ 低 | `apiGet`/`apiPost` 的返回类型依赖于 `response.data as T` 的类型断言，而非运行时验证。建议使用 zod 或 io-ts 进行运行时类型校验 |
| F9 | ℹ️ 低 | 没有请求去重或取消机制——如果用户快速点击多次"查询"按钮，会发起多个并行请求 |

### 4.4 查询页与组件

**文件**：`QueryPage.tsx`, `QueryInput.tsx`, `ResultTable.tsx`, `SqlPreview.tsx`

**优点**：
- `QueryPage` 根据状态(loading/error/empty/result)渲染不同 UI，状态转换清晰
- `QueryInput` 支持受控和非受控双模式——灵活但需要注意
- `ResultTable` 有客户端排序和分页
- SQL 预览仅对 ADMIN 角色可见(`isAdmin() && sql &&`)
- 收藏功能有 loading 状态和乐观 UI 更新

**问题**：

| # | 严重度 | 描述 |
|---|--------|------|
| F10 | ⚠️ 中 | `QueryInput` 的 controlled/uncontrolled 混合模式增加了复杂度。父组件 `QueryPage` 既传 `value`/`onChange`(controlled)，组件内部又有本地 state(uncontrolled)。这两种模式的行为在 React 中有细微差异(stale props)，建议统一为 controlled |
| F11 | ⚠️ 中 | `ResultTable` 使用 `index` 作为 `rowKey`，这在排序后会导致行 key 错位。Ant Design Table 依赖 rowKey 进行行更新和选择，应使用数据中的唯一标识(如 name 或组合 key) |
| F12 | ℹ️ 低 | `handleRetry` 直接使用 `lastQuestion` 和 `currentOrg` 重试，但没有考虑用户可能已切换组织 |
| F13 | ℹ️ 低 | `SqlPreview` 组件使用 `dangerouslySetInnerHTML` 渲染格式化的 SQL，需要确保格式化库的输出是安全的 |

## 8. 正面亮点

以下是项目中值得特别肯定的设计和实现：

### 安全设计
- **JSqlParser AST 级 SQL 校验** —— 这是安全设计的典范，在多处体现了深度防御(multi-layer defense)：禁止 DML/DCL、禁止系统 schema、禁止 SELECT *、禁止危险函数、强制 LIMIT 注入、org scope 验证
- **JWT Secret 强度校验** —— 启动时检查密钥长度、字符多样性、连续/重复模式
- **Redis Sorted Set 滑动窗口限流** —— 比固定窗口计数器准确得多
- **审计日志 upsert 模式** —— 使用 PostgreSQL `ON CONFLICT ... DO UPDATE` 避免竞态条件

### 架构设计
- **Orchestrator 管道模式** —— 清晰的步骤分离，每步可独立测试
- **LLMAsyncExecutor 独立 Bean** —— 正确解决了 Spring `@Async` 自调用代理失效问题
- **Rule 1 严格执行** —— `summarizeResults(ResultProfile)` 确保 LLM 绝不接触业务数据
- **Prompt 外置化** —— 模板文件与 Java 代码分离，便于非开发人员调整

### 代码质量
- **异常分类** —— `classifySqlError()` 基于 PostgreSQL SQLSTATE 码判断错误类型，匹配准确
- **缓存键语义版本** —— `t2r:cache:query:v2:` 前缀便于缓存策略升级
- **MetadataService 混合 RAG** —— 向量检索 + 关键词回退 + SQL Example 表名增强，三层递进

### 前端
- **Zustand + persist** —— 轻量且功能完备的状态管理
- **ECharts 自适应图表类型推断** —— 根据数据特征(时序/维度/指标数量)智能选择可视化
- **SQL 仅管理员可见** —— 前后端双重控制(GET 返回 null + 前端条件渲染)
- **TypeScript 全栈类型** —— 从 API 类型到组件 Props 类型链完整
