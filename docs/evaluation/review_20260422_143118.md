## S1 架构红线审查结果
### Rule 1: LLM只看元数据
基本通过，但有日志侧风险。`OrchestratorService` 生成 SQL 时传入 `metadataJson`、组织路径/ID和用户问题，未发现把查询结果 rows 传入 SQL 生成 Prompt 的路径（backend/src/main/java/com/text2report/service/OrchestratorService.java:160-177）。结果摘要只传入 `ResultProfile`，未传原始行（backend/src/main/java/com/text2report/service/OrchestratorService.java:242-246；backend/src/main/java/com/text2report/service/llm/OpenAILLMService.java:97-106）。但 LLM 调用日志记录完整自然语言问题，若用户问题包含敏感信息会落日志（backend/src/main/java/com/text2report/service/llm/OpenAILLMService.java:64-65）。

### Rule 2: SqlGuard不可绕过
违反。主查询链路会先 `sqlGuardService.validate()` 和 `validateOrgScope()` 再执行（backend/src/main/java/com/text2report/service/OrchestratorService.java:203-210），`QueryExecutorService` 使用 `PreparedStatement` 执行已校验 SQL（backend/src/main/java/com/text2report/service/QueryExecutorService.java:49-59）。但存在业务库直连绕过：`OrgService.syncFromBusiness()` 通过 `businessJdbcTemplate.query()` 直接查业务库（backend/src/main/java/com/text2report/service/OrgService.java:104-109），`HealthController` 也直接对 `businessDataSource` 执行 `SELECT 1`（backend/src/main/java/com/text2report/controller/HealthController.java:76-103）。

### Rule 3: 业务库只读
部分通过。配置层 `spring.datasource.business.hikari.read-only: true` 存在（backend/src/main/resources/application.yml:21-24；backend/src/main/resources/application-local.yml:15-21），`SqlGuardService` 基于 JSqlParser 阻断 INSERT/UPDATE/DELETE/DROP/TRUNCATE/MERGE/EXEC/ALTER（backend/src/main/java/com/text2report/service/SqlGuardService.java:129-154）。但直连业务库路径未经过 SqlGuard，仍违反“所有 SQL 执行必须经过网关”的架构红线。

### Rule 4: 每次请求可审计
基本通过。查询开始、成功、缓存命中、异常和 SqlGuard 阻断路径均会写审计（backend/src/main/java/com/text2report/service/OrchestratorService.java:95-123；backend/src/main/java/com/text2report/service/AuditService.java:35-62,110-188）。审计字段包含 requestId、userId、orgId、question、SQL、状态、执行时间、行数等（backend/src/main/resources/mapper/meta/AuditQueryLogMapper.xml:52-86）。需注意审计 prompt 只做 API key/token 样式脱敏，未对用户问题中的敏感文本做处理（backend/src/main/java/com/text2report/service/AuditService.java:229-243）。

## S2 安全漏洞
### [P0] 明文生产级凭据提交在配置文件中
- **位置**: backend/src/main/resources/application-local.yml:11-13,23-25,34-36,55-57,67-76；backend/src/main/resources/application.yml:45-47
- **描述**: 本地配置文件包含公网 PostgreSQL、Redis、JWT secret、DeepSeek API key 等明文凭据；主配置还给 `VECTOR_DB_PASSWORD` 提供了明文默认密码。
- **风险**: 仓库泄露即可直接连接数据库/Redis或调用 LLM API；攻击者还可能伪造本地环境 JWT，属于凭据泄露级别风险。
- **建议**: 立即吊销并轮换已暴露凭据；删除提交中的明文密钥；所有密码/API key/JWT secret 仅允许来自环境变量或密钥管理系统，默认值应为空且启动失败。

### [P0] 业务库存在绕过 SqlGuard 的直连查询路径
- **位置**: backend/src/main/java/com/text2report/service/OrgService.java:104-109；backend/src/main/java/com/text2report/controller/HealthController.java:76-103
- **描述**: `OrgService` 和 `HealthController` 直接使用业务库 `JdbcTemplate/DataSource` 执行 SQL，未通过 `SqlGuardService` 或 Query Gateway。
- **风险**: 当前语句是固定 SELECT，但该模式打破“只有查询网关可访问数据库”的红线，后续维护中容易扩展出未审计、未限流、未策略校验的数据访问路径。
- **建议**: 将业务库访问收敛到 Query Gateway；健康检查可改为连接池级探活或纳入只读受控检查；组织同步应有独立受控数据同步网关并记录审计。

### [P1] 查询组织范围允许前端传入 orgId
- **位置**: backend/src/main/java/com/text2report/model/dto/QueryRequest.java:13-17；backend/src/main/java/com/text2report/controller/QueryController.java:45-49；backend/src/main/java/com/text2report/service/OrchestratorService.java:127-151
- **描述**: `orgId` 是请求体必填字段，编排层优先采用 `requestedOrgId`，之后再检查可访问列表。
- **风险**: 与“组织隔离强制从 JWT 载荷获取 orgId，禁止前端覆盖”的检查项不一致。虽然有 accessibleOrgIds 校验，但用户可主动探测自己授权集合内的任意组织范围，审计语义也依赖前端输入。
- **建议**: 默认使用 JWT/服务端会话解析组织上下文；如允许组织选择，应由服务端授权列表和显式切换接口驱动。

### [P1] JWT 登出未写入黑名单，黑名单检查形同未闭环
- **位置**: backend/src/main/java/com/text2report/security/JwtAuthFilter.java:183-191；backend/src/main/java/com/text2report/service/AuthService.java:75-85
- **描述**: 过滤器每次请求检查 `t2r:jwt:blacklist:*`，但 `logout()` 只删除当前 session key，没有把 token 写入 blacklist。
- **风险**: 当前依赖 session jti 删除实现失效，但黑名单机制不完整；如果后续放宽单会话校验或 Redis 出现状态不一致，登出令牌可能继续可用。
- **建议**: 登出时按 token 剩余 TTL 写入 Redis 黑名单，或删除未使用的黑名单路径并统一以 session jti 机制表达。

### [P1] LLM 相关日志记录用户原始问题和 SQL
- **位置**: backend/src/main/java/com/text2report/service/llm/OpenAILLMService.java:64-65,97-101,122-124
- **描述**: SQL 生成、摘要、修复日志直接记录自然语言问题和待修复 SQL。
- **风险**: 用户问题可能包含客户名、订单号、财务数字等敏感信息；生成 SQL 也可能暴露表结构与组织条件，进入应用日志后扩大可见面。
- **建议**: 日志中仅记录 requestId、orgId、长度、hash、状态；详细内容进入受控审计表并按权限查看。

### [P1] 生产配置允许详细错误 message/binding errors
- **位置**: backend/src/main/resources/application.yml:171-178
- **描述**: `server.error.include-message: always` 和 `include-binding-errors: always` 在主配置中开启。
- **风险**: 未被 `GlobalExceptionHandler` 捕获的 Spring 错误可能返回内部异常消息、字段绑定细节或路径信息。
- **建议**: 生产配置设为 `never` 或按环境区分，仅开发环境开启。

### [P1] 向量检索 topK 无上限
- **位置**: backend/src/main/java/com/text2report/controller/EmbeddingController.java:39-52；backend/src/main/java/com/text2report/service/EmbeddingService.java:58-64；backend/src/main/resources/mapper/vector/MetaEmbeddingMapper.xml:17-23
- **描述**: 管理接口直接使用请求体 `topK` 作为 SQL LIMIT，未设置最大值。
- **风险**: 管理账号或被盗 token 可请求超大 topK，造成向量库高 CPU/内存消耗。
- **建议**: 对 topK 加 `@Min/@Max`，服务层再次 clamp 到安全上限。

## S3 健壮性问题
### [P1] SqlGuard 组织范围校验不支持要求文档中的递归子树 SQL 模式
- **位置**: backend/src/main/java/com/text2report/service/SqlGuardService.java:312-381
- **描述**: `validateOrgScope()` 只接受 `org_id = literal` 或 `org_id IN (literal list)`；当右侧是子查询/CTE 时直接返回 false。
- **风险**: 项目规范推荐的 `WHERE org_id IN (WITH RECURSIVE subtree ...)` 会被判定为缺少组织范围，导致合规 SQL 被阻断。
- **建议**: 明确 Demo 阶段只允许字面量列表，或扩展 AST 校验以识别受控递归子树查询。

### [P2] 历史/审计分页缺少最大页大小
- **位置**: backend/src/main/java/com/text2report/controller/QueryController.java:52-62；backend/src/main/java/com/text2report/service/HistoryService.java:30-49；backend/src/main/java/com/text2report/controller/AuditController.java:36-53；backend/src/main/java/com/text2report/service/AuditQueryService.java:50-73
- **描述**: `pageSize` 只做下限处理，未设置上限。
- **风险**: 大页请求会导致数据库扫描、网络传输和 JVM 内存压力，影响可用性。
- **建议**: Controller DTO 使用 `@Max`，服务层 clamp，例如历史 100、审计 200。

### [P2] 用户管理分页 size 缺少上限且服务层内存分页
- **位置**: backend/src/main/java/com/text2report/controller/UserController.java:41-49；backend/src/main/java/com/text2report/service/UserServiceImpl.java:125-138
- **描述**: `size` 无上限，服务层先取全量用户再 `subList`。
- **风险**: 用户量上升后容易造成慢查询和内存压力。
- **建议**: Mapper 层分页查询，Controller/Service 同时限制最大 size。

### [P2] DDL 确认后异步 embedding 在事务提交前触发
- **位置**: backend/src/main/java/com/text2report/service/DDLParserService.java:112-176；backend/src/main/java/com/text2report/service/EmbeddingService.java:53-56
- **描述**: `confirmAndSave()` 在 meta 事务中调用 `embedAndStoreAsync()`，未使用 afterCommit 钩子。
- **风险**: 如果后续事务回滚，向量库可能已写入对应表描述，造成元数据与向量索引不一致。
- **建议**: 使用 `TransactionSynchronizationManager.registerSynchronization(... afterCommit ...)` 或事件监听 `@TransactionalEventListener(AFTER_COMMIT)`。

### [P2] Redis session 校验失败未降级，Redis 短暂不可用会导致全站 401/500 风险
- **位置**: backend/src/main/java/com/text2report/security/JwtAuthFilter.java:138-143；backend/src/main/java/com/text2report/service/AuthService.java:138-140
- **描述**: 黑名单检查有异常降级，但 `isCurrentSession()` 和 `getCurrentJti()` 未捕获 Redis 异常。
- **风险**: Redis 抖动时认证链路会抛异常，导致已登录用户请求失败。
- **建议**: 明确 fail-closed/fail-open 策略；若 fail-closed，应返回统一 503/401 并告警；避免未处理异常穿透。

## S5 代码合理性问题
### [P2] `AuthService` 通过反射访问 `JwtUtil` 私有成员
- **位置**: backend/src/main/java/com/text2report/service/AuthService.java:157-190
- **描述**: 为生成带 jti 的 token，服务层反射调用私有 `getSecretKey()` 并读取私有 `expirationMs`。
- **风险**: 破坏封装，重构 `JwtUtil` 时容易运行期失败；安全关键代码难以测试和审计。
- **建议**: 在 `JwtUtil` 暴露 `generateToken(..., jti)` 或统一 token 构造方法。

### [P3] `OrchestratorService` 职责偏重
- **位置**: backend/src/main/java/com/text2report/service/OrchestratorService.java:95-264
- **描述**: 同时负责组织解析、权限校验、元数据检索、Prompt 构造、LLM 调用、SQL 修复、执行、图表推荐、摘要、审计、缓存。
- **风险**: 后续策略变更容易产生回归，单元测试粒度偏粗。
- **建议**: 按权限/上下文解析、SQL 生成与修复、执行与渲染组装拆成更小协作者。

### [P3] `DataSourceDTO`/前端表单包含密码字段，但 API 转换未提交密码
- **位置**: frontend/src/services/dataSourceApi.ts:40-50,63-72；backend/src/main/java/com/text2report/model/dto/DataSourceDTO.java:26
- **描述**: 前端 `toBackendDataSource()` 没有映射 `password`，创建/更新数据源时表单密码不会传给后端。
- **风险**: 数据源管理功能表现与 UI 不一致，排查成本高。
- **建议**: 明确当前是否禁用密码更新；若启用，前端 payload 与后端 DTO 需对齐，并保证后端加密存储。

## 总体评价
项目主查询链路已具备元数据 Prompt、LLMService 抽象、AST SQL Guard、只读执行和审计闭环，但配置泄密和业务库直连绕过网关是必须优先处理的红线问题；分页、事务后异步、接口契约也需要收敛。
