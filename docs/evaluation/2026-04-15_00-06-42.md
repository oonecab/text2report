评估时间：2026-04-15 00:06:42

评估方式：静态代码阅读 + 文档核对 + 本地命令验证

## 1. 执行摘要

Text2Report 已经不是“空骨架”项目，而是一个进入 Demo 联调后期的半成品系统。前后端目录、核心页面、后端控制器、编排服务、元数据服务、SQL Guard、审计、认证、限流、缓存、Prompt 模板、SQL 初始化脚本和测试体系都已经具备，整体工程组织度明显高于普通原型项目。

如果以 AGENTS.md 中描述的目标来衡量，这个项目当前最接近的状态是：

- 已具备“可演示的主链路后端 + 较完整的管理与查询界面”
- 后端成熟度显著高于前端成熟度
- 架构方向总体正确，但关键企业级约束尚未完全闭环
- 当前不能直接判定为“Demo 就绪”或“可验收完成”

本次评估的总体判断如下：

| 维度 | 结论 | 说明 |
|------|------|------|
| 架构方向 | 良好 | 前后端分离、Prompt 外置、LLM 接口化、AST 校验、审计与权限模型均已成型 |
| 后端完成度 | 较高 | 查询编排、元数据、组织树、审计、认证、缓存、限流都已落地 |
| 前端完成度 | 中等偏上 | 页面覆盖面广，但当前分支存在构建失败，影响“可交付状态” |
| 安全控制 | 中等 | 已做很多正确工作，但组织权限注入仍未在 SQL 层强制闭环 |
| 与目标架构一致性 | 中等偏低 | 当前实现明显偏 PostgreSQL，不是 AGENTS.md 目标中的 SQL Server 只读网关形态 |
| 文档可信度 | 中等偏低 | `docs/STATUS.md` 与 `docs/testing/e2e-test-checklist.md` 和仓库当前真实状态有漂移 |

一句话结论：

该项目已经具备继续推进的良好基础，但当前最大问题不是“功能没写”，而是“目标架构与当前实现之间仍有关键偏差，且项目状态文档已经开始落后于代码实际情况”。

## 4. 与 AGENTS.md 核心约束的符合度评估

### 4.1 约束一：LLM 只能看元数据，不能看业务数据

结论：大体符合，但仍需要继续守住边界。

正向证据：

- `LLMService` 设计明确把 SQL 生成输入限制在问题、元数据 JSON、组织 ID
- `MetadataService.buildMetadataJson()` 构建的是表、字段、术语、JOIN、示例等元数据
- `OpenAILLMService.summarizeResults()` 接收的是 `ResultProfile`，不是原始结果行
- `QueryResultDTO` 的摘要逻辑没有把明细数据直接交给 LLM
- `AuditService` 对 prompt 日志做了脱敏与长度截断

风险点：

- 当前仍会把完整 prompt 文本以脱敏后的形式存入审计日志，虽然没有明显看到业务数据泄漏路径，但后续仍应审计 prompt 内容构造过程
- 若未来在摘要、修复或推荐图表环节修改接口，必须继续维持“不传原始结果行”这一边界

总体评价：

- 该约束目前属于“设计正确、实现基本到位”

### 4.2 约束二：只有查询网关可以访问数据库

结论：大体符合，但“网关”的实现形态更像后端内部服务，而不是独立网关层。

正向证据：

- 前端没有直接数据库访问路径
- 控制器并不直接操作业务库
- 查询执行集中在 `QueryExecutorService`
- SQL 安全校验集中在 `SqlGuardService`

偏差点：

- AGENTS.md 中强调的是“只有 query gateway 可访问数据库”，当前实现是 Spring Boot 内部服务调用，并没有形成明显独立的“query gateway”边界组件
- 这在 Demo 阶段可以接受，但从企业级视角看，未来最好把“SQL Guard + 权限校验 + 超时/limit 注入 + 执行”抽成更明确的网关层

总体评价：

- 该约束在职责划分上基本满足，在部署形态上还不够彻底

### 4.3 约束三：生产只允许只读 SQL

结论：部分符合，但还没有达到 AGENTS.md 目标里的 SQL Server 只读生产路径标准。

正向证据：

- `SqlGuardService` 使用 JSqlParser 做 AST 解析，而不是 regex 黑名单
- 明确阻断 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`TRUNCATE`、`MERGE`、`EXEC/EXECUTE`、`ALTER`
- Hikari 业务数据源配置了 `read-only: true`
- 默认注入结果限制

关键偏差：

- 当前默认业务数据库不是 SQL Server，而是 PostgreSQL
- `SqlGuardService.injectLimit()` 注入的是 `LIMIT`，不是 SQL Server 目标中的 `TOP N`
- `prompts/sql_generation_v1.txt` 明确要求使用 PostgreSQL 语法
- `OpenAILLMService` 和 `PromptBuilder` 里方言参数默认也是 `postgresql`
- `QueryExecutorService.classifySqlError()` 的错误分类明显偏 PostgreSQL 错误码

总体评价：

- 只读约束本身做得不错
- 但“只读 SQL Server 生产路径”尚未实现完成

### 4.4 约束四：每个请求都必须可审计、可感知权限

结论：审计能力较好，权限能力中等，但“组织权限强制注入”尚未闭环。

正向证据：

- `TraceContext` + `X-Request-ID` 已形成链路追踪
- `AuditService` 记录开始、成功、失败、缓存命中、反馈等事件
- `SecurityConfig` 配置了认证、角色授权、401/403 统一返回
- `JwtAuthFilter` 会把用户、角色、组织信息写入上下文
- `QueryController` 对普通用户隐藏 SQL 文本
- 限流和请求日志过滤器也已接入

关键风险：

- 组织范围目前主要依赖 prompt 中提示 LLM 生成 `WHERE org_id IN (...)`
- 我没有看到在 SQL Guard 或执行前对组织过滤进行 AST 级强制注入或强校验
- 这意味着只要 LLM 漏加、错加或绕过组织条件，执行层没有第二道“强制权限闭环”

总体评价：

- 可审计方面明显比可感知权限更成熟
- 真正的“permission-aware”还没有完全落地

## 5. 分模块评估

### 5.1 前端评估

前端完成面比较广，说明项目已经过了“只做查询首页”的阶段。

已具备的正向能力：

- 查询域页面存在：`QueryPage`、`HistoryPage`、`FavoritesPage`
- 管理域页面存在：组织树、DDL 上传、表管理、术语、JOIN、示例、审计、数据源管理
- 路由和鉴权结构明确，普通用户域与管理员域分离
- 使用 React + Ant Design + Zustand，技术栈稳定
- 查询结果具备摘要、图表、表格、SQL 展示等视图

当前明显问题：

- 前端构建失败，说明当前主线代码处于“不完全可交付”状态
- 构建错误集中在 DDL 解析接口契约漂移和类型不一致
- `frontend/src/components/admin/DDLEditor.tsx` 认为返回对象存在 `tables`
- `frontend/src/types/metadata.d.ts` 中 `DDLParseResult` 却定义为单表结构
- `frontend/src/services/request.ts` 存在未使用的 `App` import，触发 TypeScript 构建失败

构建失败的直接错误包括：

- `DDLEditor.tsx` 中 `result.tables` 属性不存在于 `DDLParseResult`
- `result.tables.map((t) => ...)` 中 `t` 类型未声明
- `request.ts` 中 `App` 未使用

结论：

- 前端“页面数量”已经比较像一个完整 Demo
- 但“当前分支质量状态”并不支持文档里声称的“构建已通过”

### 5.2 后端评估

后端是当前项目最强的一部分。

正向表现：

- 控制器、服务、配置、DTO、Mapper、XML 映射和测试结构完整
- `OrchestratorService` 已把元数据检索、组织解析、LLM 生成、SQL Guard、执行、缓存、审计串起来
- `SqlGuardService` 使用 AST 做安全验证，方向正确
- `AuditService` 处理了异步审计和 ThreadLocal 丢失问题
- `SecurityConfig`、`JwtAuthFilter`、`RateLimitFilter` 等配套相对齐全
- 测试覆盖了 DDL 解析、PromptBuilder、LLM 服务、SQL Guard、Orchestrator、缓存、反馈、收藏、历史等关键类

限制与问题：

- 编排层当前仍然把方言写死为 PostgreSQL
- `resolveDatasourceId()` 直接取第一个 active datasource，不是真正的数据源路由
- 组织权限没有被强制注入到最终 SQL
- `LocalLLMService` 只是占位实现
- 当前业务数据库配置并未体现 SQL Server 专属执行链路

结论：

- 后端从“工程完整度”角度看已经较成熟
- 从“与目标生产架构一致性”角度看仍有关键缺口

### 5.3 元数据与 DDL 管线评估

这一块已经具备 Demo 所需的主骨架。

优点：

- `MetadataService` 已支持表、字段、术语、JOIN、示例的读取和 CRUD
- `DDLParserService` 已支持行内注释、`sp_addextendedproperty`、`COMMENT ON COLUMN`
- `MetadataController` 已提供 `/ddl/parse` 和 `/ddl/confirm`
- 前端也有对应的解析预览与字段补充流程

不足：

- DDL 解析本质上仍是 regex 驱动，不是完整 SQL 语法树解析
- 对复杂 DDL、跨 schema、多约束、多行复杂定义的鲁棒性可能有限
- 元数据检索当前主要靠简单 `LIKE`，还不够“业务语义化”
- `org_scope`、`datasource_scope`、敏感字段等治理信息没有在 prompt 检索时得到充分利用

结论：

- 管线存在且能支撑 Demo
- 距离“企业级元数据治理”还有明显距离

### 5.4 Prompt 与 LLM 层评估

优点：

- Prompt 模板独立存储在 `/prompts/`
- `LLMService` 接口化设计符合 AGENTS.md 要求
- `OpenAILLMService` 与 `LocalLLMService` 已按 provider 分离
- 输出要求是 JSON，符合结构化输出方向

问题：

- 当前 prompt 明确写的是 PostgreSQL 规则，不是 SQL Server 规则
- `LocalLLMService` 仅抛出“not configured yet”
- `detectIntent()` 仍主要是关键词规则，不是真正语义检测
- 图表推荐逻辑也较简化

结论：

- LLM 抽象层搭好了
- 但“从外部 API POC 平滑迁移到本地模型”的后半段还没有开始真正实现

### 5.5 安全、审计、可运维性评估

优点：

- JWT 鉴权、角色控制、统一异常返回已经具备
- 请求日志、Trace、审计、限流、缓存都已经纳入主干
- Redis 不可用时多数路径支持降级
- 普通用户看不到 SQL，符合前端展示约束

不足：

- 权限约束更像“应用层约束”，尚未升级为“查询层硬约束”
- 真正面向 SQL Server 的执行限制、方言适配和权限强校验尚未完成
- 暂未看到更细粒度的字段级敏感控制在实际查询生成过程中的使用

结论：

- 运维和安全意识明显存在
- 但距离“企业内网安全可交付”还有一段路

## 7. 关键问题与风险清单

以下问题建议按优先级处理。

### P0 级问题

#### P0-1：目标架构要求 SQL Server，但当前主链路仍是 PostgreSQL 思维

证据：

- `backend/src/main/resources/application.yml`
- `prompts/sql_generation_v1.txt`
- `backend/src/main/java/com/text2report/service/OrchestratorService.java`
- `backend/src/main/java/com/text2report/service/PromptBuilder.java`
- `backend/src/main/java/com/text2report/service/SqlGuardService.java`
- `sql/schema-business.sql`

影响：

- 项目与 AGENTS.md 中“SQL Server 只读查询路径”存在架构偏差
- 真实切到 SQL Server 时，Prompt、方言校验、错误分类、SQL 注入策略都会继续返工

判断：

- 这是当前最大的架构一致性问题

#### P0-2：组织权限没有在 SQL 层强制闭环

证据：

- `OrchestratorService` 只是把 `org_ids` 放进 prompt
- `SqlGuardService` 没有组织过滤 AST 校验或注入
- `QueryExecutorService` 直接执行校验后的 SQL

影响：

- 一旦 LLM 生成 SQL 漏掉组织条件，系统仍可能执行越权查询
- 这与 AGENTS.md 中“Every request must be auditable and permission-aware”存在实质缺口

判断：

- 这是比“方言不一致”更直接的业务风险

#### P0-3：前端当前分支无法构建

证据：

- 本次执行 `npm run build` 失败
- 主要错误在 `frontend/src/components/admin/DDLEditor.tsx` 和 `frontend/src/services/request.ts`

影响：

- 阻断“前端生产构建通过”的基本交付条件
- 也意味着 `docs/STATUS.md` 和 `docs/testing/e2e-test-checklist.md` 的相关结论失真

判断：

- 这是当前最应立即修复的交付阻断问题

### P1 级问题

#### P1-1：状态文档与实际代码状态发生漂移

证据：

- `docs/STATUS.md` 声称前端构建已通过
- `docs/testing/e2e-test-checklist.md` 仍把 “`npm run build` 通过”列为已完成前置判断背景
- 当前仓库实际构建失败

影响：

- 团队对项目 readiness 的共识会被误导
- 后续里程碑判断会失真

#### P1-2：数据源路由能力尚未真正形成

证据：

- `OrchestratorService.resolveDatasourceId()` 当前只是取第一个 active datasource
- `MetaDatasource.db_type` 存在，但查询主链路没有真正根据其决定方言或执行器

影响：

- 多数据源、按组织/按库路由的能力还停留在元数据层
- “一个 parent company + 3 subsidiaries” 的真实复杂度尚未被系统完全吸收

#### P1-3：DDL 解析对复杂场景的可靠性有限

证据：

- `DDLParserService` 主要依赖 regex

影响：

- 对实际企业 DDL 的适应能力可能弱于 Demo 假设
- 导入体验可能在复杂脚本下不稳定

#### P1-4：本地模型切换能力只有接口，没有实现

证据：

- `LocalLLMService` 全部为 `not configured yet`

影响：

- AGENTS.md 中“逐步从外部模型迁移到本地模型”的路径尚未进入实作阶段

#### P1-5：元数据检索治理深度不够

证据：

- `MetadataService.retrieveForPrompt()` 主要基于简单关键词 `LIKE`
- 未充分利用 `org_scope`、`datasource_scope`、敏感字段等治理维度

影响：

- Prompt 上下文精准度会受限
- 随着元数据规模扩大，SQL 质量容易波动

### P2 级问题

#### P2-1：测试强在后端，前端自动化保障明显不足

表现：

- 后端测试丰富
- 前端没有看到与当前构建质量同等强度的自动验证网

#### P2-2：测试总数与状态文档中的数字存在轻微不一致

表现：

- `docs/STATUS.md` 提到 156 个用例
- 本次 surefire 汇总为 157 次测试执行

影响：

- 风险不大，但说明文档统计口径未同步更新

- 因此前端与后端并未真正进入“只差真实环境验证”的状态

## 9. 建议的整改优先级

### 第一阶段：先恢复“可交付的当前状态”

建议立即完成：

- 修复前端 `DDLParseResult` 类型与后端返回结构不一致问题
- 修复 `DDLEditor.tsx` 类型错误和 `request.ts` 未使用 import
- 重新执行 `npm run build`
- 更新 `docs/STATUS.md` 与 `docs/testing/e2e-test-checklist.md`
- 建立最基础的 CI：至少包含 `mvn test` 和 `npm run build`

这一阶段目标：

- 让仓库状态重新与文档一致
- 恢复“当前主线可构建、可说明”的基本可信度

### 第二阶段：补齐最关键的架构闭环

建议优先完成：

- 让方言与数据源类型真正联动，不再把 `postgresql` 写死
- 按 AGENTS.md 目标引入 SQL Server 执行链路
- 在 SQL Guard 或执行前增加组织过滤的 AST 级强制校验/注入
- 让 datasource 选择不再固定为“第一个 active datasource”

这一阶段目标：

- 让“企业级约束”不再只是写在 Prompt 里，而是在系统里强制执行

### 第三阶段：提升语义层与元数据治理质量

建议推进：

- 增强元数据召回排序，不只做简单 `LIKE`
- 真正利用 glossary、join graph、example、org_scope、datasource_scope
- 过滤敏感字段，避免无关字段进入 prompt
- 建立更严格的 SQL 示例管理与验证机制

### 第四阶段：推进真实环境验收

建议在前面问题解决后再执行：

- 接入真实 PostgreSQL/Redis/LLM 或最终 SQL Server/Redis/LLM 环境
- 按 `docs/testing/e2e-test-checklist.md` 逐项走查
- 验证权限、缓存、异常、边界、查询质量、审计可追溯性

## 10. 最终结论

Text2Report 当前已经具备一个相当不错的 Demo 工程基础，尤其是后端主链路、元数据治理入口、Prompt 外置、LLM 接口隔离、SQL Guard 和审计能力，整体方向是对的。

但如果严格按照 AGENTS.md 的企业级目标来衡量，当前仍存在三个不可忽视的核心问题：

- 实际实现仍偏 PostgreSQL，而不是目标中的 SQL Server 只读查询网关
- 组织权限尚未在 SQL 层强制闭环
- 前端当前分支构建失败，且文档状态已经与代码状态脱节

因此，本项目的合理评语不是“还很早”，也不是“已经完成”，而是：

“主体工程已经成型，后端基础较强，但要成为可信的企业 Demo，必须先修复当前分支质量问题，并把权限与方言两条关键架构链路补闭环。”
