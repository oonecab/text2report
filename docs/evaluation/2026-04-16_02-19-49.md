# Text2Report 架构审查与代码评估报告 (A Review from Senior Engineering Perspective)

**审查日期**: 2026-04-16
**审查人**: 资深架构师

## 1. 总体评价 (Executive Summary)

经过对 Text2Report 核心代码库的深入阅读与分析，本项目在**代码质量、架构边界、安全防御以及对业务规范 (`AGENTS.md`) 的遵从度**上表现出极高的水准。

这不是一个简单的外壳（Wrapper）项目，而是一个具备严肃企业级特征的生产级应用。其以安全和治理为核心的“网关型 Text-to-SQL”设计理念在代码库中得到了坚定的贯彻。通过 AST（抽象语法树）级别的 SQL 审查、清晰的意图识别隔离，以及面向接口的 LLM 服务调用，整个系统防御严密且极具可扩展性。

## 2. 核心架构与规范遵从度评估 (Architecture Adherence)

### 2.1 大模型接口化与业务解耦（Excellent）
代码中的 `LLMService` 接口设计非常成功。由 `OpenAILLMService` 负责实现对外部 API 的请求，代码不仅强制约束了大模型返回 `json_object` 以保障反序列化成功，而且针对 SQL 生成、结果摘要合并、SQL 自愈修复等职责进行了精准的拆分。
核心的业务编排 `OrchestratorService` 没有任何与具体大模型厂商绑定的代码片段，这使得未来（依据规划）切入本地自主大模型（如 `LocalLLMService`）实现了真正的**零业务侵入**。

### 2.2 真正的 SQL 门神与安全执行（Outstanding）
针对企业最关心的注入和随意查询风险，`SqlGuardService` 的实现令人印象深刻。
项目**摒弃了常规的低级正则表达式防御**，引入了成熟的 `JSqlParser` 并实现了复杂的 AST Visitor 遍历。它不仅仅局限于阻止 `INSERT/UPDATE` 或暴力的 `SELECT *`，它深入扫描了：
- `WITH`, `JOIN ON`, `IN (...)`, `EXISTS(...)` 等深层嵌套子查询。
- 防护了对 `pg_catalog`, `sys`, `information_schema` 等高危系统元数据表的探测。
- 防护了 `xp_cmdshell`, `sp_executesql` 等高危系统函数的调用。
- 通过 AST 级别的修改，系统硬性向 `PlainSelect` 节点注入 `LIMIT` 表达式（Top Count）。这几乎杜绝了绕过鉴权引发数据全表 Scan 的可能。

### 2.3 异常自愈与编排的防御性编程（Strong）
`OrchestratorService` 内部构建了一个非常健壮的 State Machine 执行流：
系统捕获 LLM 生成的问题 SQL 并交由 `QueryExecutorService` 及 `SqlGuardService` 校验后，非安全类的异常如“表找不到”、“列含糊不清”、“语法错误”，系统会自动将其抓取，再连同当前 `MetadataContext` 反馈给 `llmService.repairSQL` 触发限次重试补偿。这种“自反馈重试网络”大大提高了端到端的成功率。

### 2.4 DDL 解析与元数据闭环（Satisfactory with caveat）
`DDLParserService` 实现支持多种不同的注释书写格式（`sp_addextendedproperty`, 行内 `--`, `COMMENT ON`），这对于纳管 SQL Server 数据源的存量表单尤为友好，并且代码中自动区分了 `ddl` 派生标签和 `manual` 人工标签。这也是践行“元数据优先而非盲目微调 LLM”的核心体现。

## 3. 前端与网络通信 (Frontend Perspective)
前端通过 `request.ts` 与严谨的强类型定义封装（`QueryRequest`, `QueryResponse`）完全贯彻了架构原则。
在 `queryApi.ts` 中，API 定义仅仅起到触发后端流程及拉取格式化数据的角色。所有业务组装、图表形态推荐（`recommendChartType`）都由后端判定下发，规避了重逻辑下发到客户端引起的不稳定性。

## 4. 潜在风险与高级改进建议 (Risks & Recommendations)

尽管整体成熟度极高，但我仍针对长期的代码演进提出以下优化建议：

### 4.1 DDL 语法解析器的脆弱性 (High Prio)
当前 `DDLParserService` 对于列信息的切割严重依赖**正则表达式**：
```java
Pattern.compile("CREATE\\s+TABLE(?:IF\\s+NOT\\s+EXISTS\\s+)?(\\w+)\\s*\\(\\s*([^;]+)\\s*\\)")
```
尽管编写了嵌套深度的判定逻辑来应对 `DECIMAL(18,2)` 内部的逗号干扰，但对于非常复杂的 DDL（含有嵌套触发器、复合 CHECK 约束区块或者极端不规则的换行符），正则解析随时可能崩溃或遗漏。
**建议**：基于目前已引入的 `JSqlParser`，可以利用其自带的 `net.sf.jsqlparser.statement.create.table.CreateTable` 解析组件去直接遍历 `ColumnDefinition` 语法树节点。用真正的词法解析器替代正则表达式，一劳永逸地解决所有边界问题。

### 4.2 SQL Guard 框架的多方言兼容适配探讨 (Medium Prio)
当前应用业务场景主要针对 **SQL Server** 设置，但是 `SqlGuardService` 使用 `JSqlParser` 写入的物理结构是 `Limit` (如 PostgreSQL 标准格式) ，而非真正的 SQL Server 方言 `TOP` （虽然注释中有记录：Return AST-serialized SQL directly）。 
对于纯正的 SQL Server 驱动来说，后端生成的 `SELECT ... LIMIT 1000` 极可能造成语法异常（SQL Server 不支持标准 LIMIT 而是支持 `TOP N` 或者是 `OFFSET ... FETCH NEXT`）。
**建议**：需要扩展向 AST 中动态注入 `Top` AST 节点的逻辑，而非无条件注入 `Limit`，以确保最终 `select.toString()` 生成真正合法的 SQL Server T-SQL 方言代码。

### 4.3 `SqlGuardService` 对 `GROUP BY` 漏洞的阻断
目前安全拦截机制极为全面，但我注意到大模型经常生成非常昂贵的 `GROUP BY` 或跨层多维笛卡尔积。可以在 AST 处理层加入一个指标限制防御池：如果查询分析结果包含对超大表的非索引字段联合 `GROUP BY`，系统可以进行预警式降级，保护源数据库负载。

## 5. 结论 (Conclusion)
项目设计清晰，规范落地坚定。开发者展现出了深厚的企业级架构视野与极好的防护意识。只需在细节（特别是 DDL 解析可靠性与 SQL 方言转换一致性上）稍加打磨，当前结构完全可支撑进入生产环境承接复杂 POC。是一份极其优秀的架构答卷。
