# SqlGuard 组织范围判定风险说明与初步修改方案

## 时间

- 创建时间：2026-04-25 22:24:03（Asia/Shanghai）

## 背景

本次改动中，`SqlGuardService#validateOrgScope` 新增了“是否需要强制组织范围过滤”的前置判断：

- 命中 `fact_*` 表时，默认判定为必须带组织范围过滤
- 命中 `dim_org` 时，默认判定为必须带组织范围过滤
- 其余表默认视为可不带 `org_id` 过滤直接通过

这项改动的直接目标，是避免像 `dim_product` 这类当前不含 `org_id` 字段的全局维表查询，被错误拦截为“缺少组织范围过滤”，从而影响正常查询体验。

从当前 Demo 阶段的建模习惯来看，这个改动能解决一部分真实问题：

- 事实表通常天然带组织边界，应严格校验
- 明显的全局维表不应被强制要求 `org_id`
- 允许管理员查看部分全局元数据型结果，能降低误杀率

## 当前实现涉及的核心风险

### 1. 组织权限判定仍然是“命名规则驱动”，不是“元数据驱动”

当前 `SqlGuardService` 通过表名是否匹配 `fact_*` 或是否在固定白名单中，来决定是否必须校验组织范围。这意味着：

- 规则绑定在命名约定上，而不是绑定在数据安全属性上
- 只要表命名不规范，安全判断就可能失真
- 新增表时，开发人员必须记得同步修改 Java 代码，否则默认行为不可控

这与仓库中强调的“权限控制必须可审计、可治理、可配置”的方向不完全一致。

### 2. 存在把“组织敏感表”误判为“全局表”的风险

如果后续引入以下类型的表：

- `dim_customer`
- `dim_project`
- `reporting_snapshot`
- `agg_profit_monthly`
- `mart_gross_profit`

这些表名未必满足 `fact_*` 规则，但其数据可能明显具备组织边界，甚至天然只能在组织权限下访问。

在当前实现下，这类表只要不命中 `fact_*` 或 `dim_org`，就可能在没有 `org_id` 条件时直接放行。这样会带来两个问题：

- 原本应受组织权限控制的数据被越权查询
- 安全性依赖“大家记得把表命名成某种固定前缀”，而不是依赖系统级约束

### 3. 对“无 org_id 但可通过 join 推导组织边界”的表没有表达能力

有些表自身不含 `org_id`，但可通过 join 路径关联到组织范围，例如：

- 通过 `project_id -> project -> org_id`
- 通过 `customer_id -> customer_account -> org_id`
- 通过快照主键关联到带组织字段的事实表

当前实现把表简单分为“必须带组织过滤”和“无需组织过滤”两类，缺少第三类：

- 表本身无 `org_id`
- 但业务上并非真正全局
- 只能在满足特定 join 路径时才允许查询

这意味着后续如果系统规模扩大，仅靠当前规则很难表达“可推导组织边界”的安全要求。

### 4. 审计信息不足以解释为何本次 SQL 被放行

当前实现可以校验 SQL 是否包含组织范围，但没有输出更细的审计解释，例如：

- 本次 SQL 命中了哪些表
- 哪些表被判定为 `global`
- 哪些表被判定为 `org_scoped`
- 本次为何跳过组织范围校验

当后续出现安全争议时，单靠“SQL 被通过了”很难快速定位是：

- 表分类错误
- SQL 缺少约束但被误放行
- 还是产品上本就允许全局查询

## 本次改动的合理性判断

这次改动并不等同于“立即存在明显漏洞”，但它属于一种“可工作的过渡方案”：

- 好处：减少了对全局维表的误杀，短期内改善了 SQL 生成和执行体验
- 代价：组织权限判定逻辑仍依赖命名推断，长期有误放行风险

因此更准确的结论是：

> 当前改动可以接受为 Demo 阶段的临时修复，但不应被视为最终版组织权限控制方案。

## 建议的初步修改方案

### 方案目标

把“是否需要组织范围约束”的判断，从 Java 命名规则，升级为元数据驱动。

### 方案一：为 `meta_tables` 增加显式安全范围字段

建议为 `meta_tables` 增加类似字段：

- `scope_type`

建议取值：

- `global`
- `org_scoped`
- `derived_org_scoped`

含义如下：

- `global`：真正允许全局访问，不要求组织过滤
- `org_scoped`：表自身必须受组织权限控制，通常要求命中 `org_id`
- `derived_org_scoped`：表本身无 `org_id`，但需要通过 join 路径推导组织范围

这样一来，是否需要组织范围控制，变成表元数据的一部分，而不是硬编码在 `SqlGuardService` 中。

### 方案二：`SqlGuardService` 改为读取元数据判定范围

改造方向：

1. 在 SQL AST 中提取命中的物理表
2. 查询这些表在 `meta_tables` 中的 `scope_type`
3. 根据 `scope_type` 决定：
   - 是否必须存在组织过滤
   - 是否允许全局查询
   - 是否必须满足可推导组织边界的 join 规则

这样新表上线时，只需补充元数据，不需要再改 Java 常量或前缀规则。

### 方案三：为 `derived_org_scoped` 补充 join 约束能力

后续可以在元数据中增加：

- 允许的组织推导路径
- 关键 join 字段
- 是否允许单表直接查询

例如可扩展到：

- `meta_join_edges` 中标记“可用于组织边界推导”
- 或新增专门的组织推导规则表

这样 `SqlGuardService` 可以拒绝：

- 不带组织范围
- 又无法通过合法 join 推导出组织边界

的 SQL。

### 方案四：增加审计输出

建议在审计日志中记录以下信息：

- 引用表列表
- 每张表的 `scope_type`
- 最终安全判定结果
- 若被放行，放行原因
- 若被拒绝，拒绝原因

这有助于后续排查和合规审计。

## 建议的实施顺序

1. 先保留当前修复，避免继续误杀明显的全局维表
2. 在元数据模型中补充 `scope_type`
3. 将 `SqlGuardService` 的强制组织范围判定切换为元数据读取
4. 再补充 `derived_org_scoped` 的 join 推导校验
5. 最后完善审计落库字段和前端展示

## 对本次改动的建议结论

本次改动可以合入，但建议明确标注为：

- “降低误拦截的过渡修复”
- “后续需要以元数据驱动的组织范围控制替换”

如果后续继续沿用当前命名推断方案而不升级，会在表规模扩大、命名不统一、组织边界复杂化后逐渐放大安全隐患。
