本报告面向具备工程设计、系统演进、架构治理与交付责任的资深开发人员撰写。报告目标不是简单枚举技术栈，也不是把目录结构转换成文字，而是结合当前仓库中的真实代码、配置、脚本、文档和测试产物，对 Text2Report 项目进行完整的技术透视。报告重点回答五个问题：

1. 这个项目在业务和系统层面究竟在解决什么问题。
2. 当前代码已经实现了哪些关键能力，哪些仍停留在设计或待验收状态。
3. 各层架构如何协同，尤其是自然语言查询、元数据检索、SQL 生成、安全校验、只读执行、结果渲染和审计之间的闭环。
4. 当前工程实现中哪些设计是正确且可持续的，哪些位置已经出现技术债、边界漂移或一致性问题。

## 2. 项目本质与业务边界

### 2.1 项目的本质不是聊天，而是受控查询编排

从 `AGENTS.md`、`README.md`、后端主链路实现和前端页面结构综合判断，Text2Report 的本质是一个“自然语言到报表”的受控查询系统，而不是开放式对话机器人。系统试图解决的不是“让模型知道所有事”，而是“让模型在严格受限的企业语义与权限边界内，生成可执行、可审计、只读的报表查询”。

这一点非常关键。因为一个通用聊天系统可以接受模糊上下文、非结构化输出和低可追责性；而这个项目的业务目标恰恰相反，它要求：

- 输入必须是受控业务问题。
- LLM 只能基于元数据工作，不能直接接触真实经营数据。
- SQL 必须经过网关与 AST 安全校验。
- 业务库访问必须通过只读路径完成。
- 查询行为必须留痕，并受组织权限约束。

这意味着该项目从第一天起就不是“把 LLM 接到数据库上”的低门槛演示，而是在尝试构建一个企业内控场景下的查询编排系统。

### 2.2 当前业务域的收敛程度很高

当前仓库明确将场景限制在毛利类报表，数据域主要围绕：

- 组织：母公司、子公司、部门
- 产品
- 渠道
- 毛利事实数据

这种收敛是合理的。因为 NL2SQL 系统如果一开始覆盖宽领域、复杂口径、多种权限与多数据源，通常会在语义、治理和验证三个层面同时失控。Text2Report 的当前做法更像企业系统的正确起步方式：先围绕一个具有代表性的指标域打通端到端链路，再逐步扩展。

### 2.3 四条核心不变量已经深度嵌入设计

项目顶层文档明确提出四条不变量：

1. LLM 看到的是元数据，不是业务数据。
2. 只有查询网关才能访问数据库。
3. 生产只允许只读 SQL。
4. 每次请求都必须可审计且带权限上下文。

从当前代码实现来看，这四条不变量并非停留在文档口号层面，而是已经进入系统结构。后文会分别论证，但先给出总体判断：

- 第一条已经基本落到运行时元数据 JSON 与摘要约束上。
- 第二条在业务查询路径上已经成立，在组织同步这类元数据镜像场景上存在受控例外。
- 第三条通过数据源只读配置和 JSqlParser AST 校验双重落实。
- 第四条通过 TraceContext、JWT、AuditService 与权限判断主链路基本成立。

因此，这个项目的架构出发点是成熟的，不属于“先做出来再考虑安全”的类型。

## 5. 总体架构：从问题到结果的完整闭环

### 5.1 运行时链路可以被准确还原

当前系统的主运行链路可以用一句话概括：用户在前端输入自然语言问题，后端在权限与组织上下文下组装元数据 Prompt，调用 LLM 生成结构化 SQL，经 AST 安全校验后在只读业务库执行，再将结果转成结构化表格、图表建议与摘要返回前端，并将整个过程写入审计。

如果展开成详细流程，当前实现是：

1. 用户在前端查询页输入问题并选择组织范围。
2. 前端通过统一请求层附带 JWT 和 `X-Request-ID` 调用后端查询接口。
3. 后端 TraceFilter 先建立请求级 TraceContext。
4. JWT 过滤器校验 token，解析用户、角色、默认组织等上下文。
5. QueryController 将请求交给 OrchestratorService。
6. OrchestratorService 解析组织上下文，校验用户对目标组织的访问范围。
7. MetadataService 结合关键词检索和向量检索获取表、字段、术语、JOIN、示例。
8. PromptBuilder 从 `prompts/` 加载模板，填入数据库方言、组织范围、metadata JSON 和用户问题。
9. LLMService 生成 SQL JSON 响应。
10. SqlGuardService 使用 JSqlParser 校验 SQL AST，阻止写操作、系统表访问、危险函数与 `SELECT *`，并注入 LIMIT。
11. QueryExecutorService 在业务只读数据源执行 SQL。
12. 结果列再回查元数据，补中文列名和类型信息。
13. LLMService 再基于结果轮廓而非原始业务数据生成摘要。
14. OrchestratorService 组装为标准响应 DTO。
15. AuditService 异步写入审计记录。
16. QueryCacheService 将结果按问题与组织维度写入 Redis。
17. 前端以摘要、图表、表格方式展示，管理员可查看 SQL。

这条链路并不是文档中的理想态，而是当前代码已经具备的现实能力。

### 5.2 架构方向正确的原因

这个架构之所以成立，核心在于它把最危险的三件事分开了：

- 语义理解与 SQL 生成交给 LLM，但不让它直接执行。
- SQL 执行交给独立执行层，但执行前必须经过 AST 校验。
- 元数据与运行时业务结果分离，确保模型仅见语义上下文，不见真实数据行。

这三层分离正是企业内控场景下 NL2SQL 系统的最基本前提。如果缺少任何一层，系统都会迅速滑向不可控状态。

## 6. 后端架构深度分析

### 6.1 启动与基础框架

启动类 `Text2ReportApplication` 很简洁，只做了两件事：

- 启动 Spring Boot
- 开启异步能力 `@EnableAsync`

虽然启动类简单，但这反而是一个健康信号，说明框架功能不是靠主类堆叠实现，而是通过配置类组织。

### 6.2 多数据源设计是项目的关键基础

`application.yml` 明确配置了三个数据源：

- `business`
- `meta`
- `vector`

其中：

- `business` 数据源指向业务事实库，Hikari 设置为 `read-only: true`
- `meta` 数据源用于系统内部元数据管理
- `vector` 数据源用于 `meta_embedding` 向量表

这套设计具有三个明显优点。

第一，它在物理层面降低了业务数据与治理数据混用的风险。业务查询、元数据维护、向量检索不再争用同一数据库语义空间。

第二，它使项目天然具备后续独立扩容能力。元数据库、向量库和业务库的负载模型完全不同，提前拆开有利于后期容量与故障治理。

第三，它与项目关于“LLM 只能看到元数据”的治理原则天然一致。因为元数据库本身就是模型语义上下文的来源，而不是业务结果集的复制。

### 6.3 配置层已经具备工程参数化能力

当前配置已经参数化的内容包括：

- LLM provider 与模型
- embedding 模型与维度
- SQL guard 默认限制
- JWT 密钥与过期时间
- Redis 参数
- RAG 阈值与 TopK
- CORS
- 速率限制
- Prompt 目录

这意味着项目已经不再依赖硬编码常量运行，而是具备可调行为。对企业系统而言，这是进入真实环境前的必要条件。

## 7. 控制器层：接口边界的实际划分

### 7.1 QueryController 对查询域做了完整封装

`QueryController` 暴露了：

- 提交查询
- 获取历史
- 反馈提交
- 收藏查询

它本身不承担 SQL 生成逻辑，也不直接访问数据库，而是把复杂过程全部交给 OrchestratorService 等服务。尤其值得注意的是，`submitQuery()` 返回结果前会调用 `maskSqlIfNeeded()`，对非管理员隐藏 SQL。这是一个非常好的实现细节，因为它把“管理员可审阅、普通用户不可见”的规则做进了控制器出口，而不是交给前端自觉隐藏。

### 7.2 MetadataController 已经形成治理后台的服务面

该控制器当前覆盖：

- DDL 解析与确认
- 表与字段查询
- 字段更新
- 术语词典 CRUD
- JOIN 关系 CRUD
- 示例 CRUD

这说明元数据治理并不是代码里的“隐性功能”，而是已经成为一个正式后台能力域。对 NL2SQL 系统而言，这是成熟度的重要标志，因为实际生产中的 SQL 质量更多依赖元数据治理，而不是频繁更换模型。

### 7.3 Org、User、Embedding、Audit 控制器说明系统边界已经完整

从控制器集合可以判断当前系统不仅能“查”，还能“管”。这包括：

- 管账号
- 管组织
- 做组织同步
- 管 embedding
- 查看审计

这类能力的存在使 Text2Report 更像企业内部平台，而不是单功能查询页面。

## 8. 查询编排主链路：OrchestratorService 深入解读

### 8.1 它是系统真正的中枢

`OrchestratorService` 是当前后端最核心的服务。它不只是“串调用”，而是在承担查询生命周期中几乎所有关键决策：

- 构造上下文
- 选择组织
- 校验权限
- 获取组织子树
- 获取元数据
- 组装 Prompt
- 调用 LLM
- 校验 SQL
- 修复 SQL
- 执行 SQL
- 生成摘要
- 计算信心分
- 组装响应
- 驱动审计与缓存

从系统设计角度看，这个类已经承担了典型“应用服务/编排服务”的角色。

### 8.2 QueryContext 的引入是正确的

它没有把中间状态散落在十几个临时变量中，而是使用 `QueryContext` 汇聚以下信息：

- requestId
- userId
- orgId
- orgSubtreeIds
- orgPath
- question
- intent
- metadataContext
- metadataJson
- prompt
- generatedSql
- validatedSql
- retryCount
- confidence

这种设计的价值在于：

- 审计时容易回溯完整上下文
- 重试流程中状态可持续演进
- 后续拆分编排模块时不需要重构大量方法签名

### 8.3 权限判断位置是正确的

权限判断没有放在 SQL 执行之后，也没有交给前端，而是在编排前置阶段完成：

- 先解析用户可访问 org 列表
- 再判断请求 org 是否在授权范围内
- 再计算实际可注入的组织子树

这意味着系统从语义生成阶段开始就知道查询边界，避免了“先生成宽 SQL，再在执行侧兜底裁剪”的危险模式。

### 8.4 自动修复机制是受控的

OrchestratorService 的重试逻辑不是无条件重试，而是只在可识别的错误场景下重试，例如：

- 列不存在
- 表不存在
- 关系不存在
- 语法错误
- 别名/歧义

这是一种相对成熟的策略，因为它把“模型可修复的错误”和“权限或策略阻断错误”区分开了。系统不会对权限拒绝做无意义重试，也不会把所有错误都包装成“再问一次模型”。

### 8.5 当前的主要问题是类职责已过重

从工程演进视角看，OrchestratorService 的结构虽然合理，但体量已经接近未来的维护临界点。继续在这里叠加新特性，后果通常会是：

- 逻辑耦合度持续升高
- 单测变得脆弱
- 某些行为只敢补丁式修复，不敢重构

因此，从下一阶段开始，这个类应当逐步拆分成更明确的工作流组件，而不是继续纵向增长。

## 9. 元数据体系：项目最核心的治理基础

### 9.1 项目的真正核心不是 SQL，而是元数据

Text2Report 的真正核心资产不是 LLM，也不是查询页面，而是元数据系统。因为对企业报表系统来说，模型只是在消费语义上下文，而这个语义上下文的质量完全取决于：

- 表和字段是否被正确描述
- 术语与指标是否被标准化
- JOIN 路径是否被显式建模
- 示例 SQL 是否覆盖关键场景
- 组织边界是否能注入

当前项目清楚地把这些内容集中到元数据库和 MetadataService 中，这是架构上的正确方向。

### 9.2 MetadataService 已不只是 CRUD 服务

当前的 MetadataService 具备三种能力：

1. 元数据管理能力
2. 运行时检索能力
3. Prompt 上下文装配能力

它不仅负责表、字段、术语、示例和 JOIN 的管理，还负责把这些治理资产转成运行时可供 LLM 消费的 metadata JSON。

### 9.3 混合检索策略已经落地

在 `retrieveForPrompt()` 中，系统并不是只做关键词匹配，也不是完全依赖向量召回，而是采用混合模式：

- 先从向量库检索示例、术语、表描述
- 用相似度阈值过滤
- 根据配置决定是否再回退到关键词搜索
- 把结果合并后装配成 MetadataContext

这是一个现实可用的策略。因为完全关键词搜索会丢失语义召回，完全向量搜索又容易在冷启动或 embedding 质量不稳时发生漏召回。当前这种混合模式适合项目现阶段。

### 9.4 metadata JSON 的构造方式符合治理要求

`buildMetadataJson()` 输出的内容包括：

- 数据库方言
- 表
- 字段
- 术语
- JOIN
- 示例

重要的是，它没有把业务事实数据行拼进 Prompt，也没有把结果集传给模型做二次分析。这与项目的第一条安全不变量是一致的。

### 9.5 当前元数据体系的主要问题

目前元数据体系的最大问题不是代码缺失，而是命名与文档存在历史漂移。比如：

- 文档中既出现复数表名，也出现单数表名
- 早期 SQL Server 语义与当前 PostgreSQL 实现同时存在
- 一些 DTO 字段和前端适配层体现出接口字段仍在演化

这类问题短期不会导致系统不可用，但会持续提高认知成本，并影响后续跨团队协作。

## 10. DDL 解析与元数据入库链路

### 10.1 这个功能的重要性高于表面看起来的程度

很多 NL2SQL 项目把“DDL 上传”看成后台附属功能，但在 Text2Report 中，它实际上是元数据治理的第一入口。因为只有当表、字段、注释能被批量、规范、可追溯地导入，系统才有持续扩展元数据的能力；否则元数据很快会退化成手工散乱维护的资产。

### 10.2 DDLParserService 的实现策略

当前 DDL 解析器支持：

- 行尾 `-- comment`
- `sp_addextendedproperty`
- `COMMENT ON COLUMN`
- `CREATE TABLE` 解析

解析后会输出结构化预览，由前端页面允许用户补充字段中文名和说明，再由确认接口写入元数据库。写入后系统还会异步生成表描述 embedding，并清理查询缓存。

这是一个相当合理的治理链路，因为它把“机器自动提取”和“人工业务校正”结合起来了。

### 10.3 这套解析方案的实际适用边界

必须明确指出，当前解析方案本质上是正则与字符串处理驱动的受控 parser，而不是通用 SQL DDL 编译器。因此，它的适用边界是：

- 结构相对简单的建表脚本
- 注释格式可控
- Demo 或受约束导入场景

它不适合作为通用企业异构 DDL 的强解析器。未来如果要支持更复杂的建模输入，应考虑引入更强的 DDL 解析策略，或者在上传阶段加更严格的格式约束。

## 11. LLM 抽象与 Prompt 工程

### 11.1 LLMService 接口化是本项目的重要架构决策

项目明确规定：业务编排代码不能直接调用 LLM SDK，必须通过 `LLMService`。当前代码也确实遵守了这一点。其直接价值包括：

- provider 可切换
- 测试更容易替换 mock
- 编排层不会被供应商 SDK 绑定
- 本地模型接入时影响面更小

这是一个成熟系统会做的决策，而不是原型代码会自然具备的能力。

### 11.2 OpenAILLMService 实际上承担的是“OpenAI-compatible provider adapter”

虽然类名是 OpenAI，但从配置看，默认 base URL 指向 DeepSeek 的兼容接口。这意味着这个实现本质上并不是“紧耦合 OpenAI 平台”，而是“兼容 OpenAI Chat Completion 协议的 provider 适配器”。从架构视角，这是合理的。

### 11.3 输出约束是结构化的

SQL 生成 Prompt 和 SQL 修复 Prompt 都要求模型只返回 JSON，字段包含：

- `sql`
- `explanation`
- `tables_used`
- `confidence`

同时服务端也明确用 JSON 解析，不接受自由文本。这一点非常重要，因为企业系统不能依赖“模型差不多会按要求说话”，必须把输出协议收窄。

### 11.4 PromptBuilder 的设计是健康的

PromptBuilder 通过文件读取和占位符填充实现：

- Prompt 外置
- 模板版本化
- 文件系统与 classpath 双路径支持

这避免了 Prompt 分散在 Java 代码中的问题，也便于未来做 Prompt 版本评审。

### 11.5 LLM 相关能力中的弱项也需要明确

当前系统中以下能力仍然偏启发式：

- `detectIntent()` 是关键词规则，不是真正模型分类
- `recommendChartType()` 主要基于列数和行数，不是完整图表语义推荐
- SQL 修复依赖模型，但失败场景仍以基础错误模式为主

这不代表设计错误，而是说明当前阶段重点在“打通安全闭环”，而不是“追求最强智能性”。

## 12. SQL 安全：当前系统中最成熟的一层

### 12.1 SqlGuardService 的位置非常关键

NL2SQL 系统最危险的一步不是“模型会不会胡说”，而是“错误 SQL 是否能真的执行”。Text2Report 明确把这个风险收敛到 SqlGuardService，并用 AST 校验而不是简单字符串匹配处理，这是一个决定系统上限的架构点。

### 12.2 已实现的安全能力

当前 SQL Guard 可阻止：

- INSERT
- UPDATE
- DELETE
- DROP
- TRUNCATE
- MERGE
- EXECUTE
- ALTER
- 系统 schema 访问
- 危险函数调用
- `SELECT *`
- `t.*`

同时它能够递归分析：

- CTE
- 子查询
- JOIN 条件
- WHERE
- GROUP BY
- HAVING
- ORDER BY

这说明它不是“看几个关键字”的表面防线，而是真正在遍历 SQL AST。

### 12.3 只读安全并非只靠 AST

除了 AST 校验外，业务数据源本身也被配置为只读 Hikari 连接池。这意味着即便有漏网之鱼，底层 JDBC 连接仍有第二层保护。双保险设计是合理的。

### 12.4 当前仍需关注的现实问题

虽然安全层整体成熟，但仍需要注意：

- AST 安全并不自动保证语义正确，只保证不触发明显危险行为。
- 组织过滤目前主要由 Prompt 约束驱动，系统没有在 SQL Guard 中做更强的组织过滤语义审查。
- 如果未来支持更复杂 SQL 语法，Guard 的 visitor 逻辑还需同步扩展。

这不影响当前阶段评价，但应写入后续治理计划。

## 13. 业务库执行层与结果装配

### 13.1 QueryExecutorService 的职责界定是清晰的

执行层只做三件事：

- 执行经过校验的 SQL
- 提取结构化结果
- 基于元数据补全列展示信息

它不负责生成 SQL，也不负责做业务解释。这种单一职责划分是正确的，因为执行层本应尽量稳定和可测试。

### 13.2 错误分类对自动修复非常重要

执行层会根据 SQLState 和异常消息，把错误归类为：

- column does not exist
- table does not exist
- syntax error
- ambiguous column reference
- timeout

这使上游编排层可以决定哪些错误值得交给模型修复，哪些应该立即失败。它不是一个花哨特性，而是自动修复可控性的基础。

### 13.3 结果装配遵循了前端契约

最终返回的 `QueryResultDTO` 包含：

- requestId
- sql
- table
- resultProfile
- summary
- warnings
- audit

字段命名使用 snake_case 序列化策略，与前端契约基本匹配。对普通用户隐藏 SQL、对管理员保留 SQL 的处理也已经在后端出口完成，而不是把这一责任压给前端。

## 14. 权限模型与组织体系

### 14.1 当前权限模型不是“角色即权限”，而是“角色 + 组织授权”

系统的权限不是简单地分成 admin/user 两档，而是至少包含两个维度：

- 角色：ADMIN / MANAGER / USER
- 组织授权范围：SELF / CHILDREN / ALL

这意味着系统已经从粗糙 RBAC，向“角色 + 数据域范围”的组合模型演进。

### 14.2 组织体系以 dim_org 为准

当前后端以元数据库中的 `dim_org` 为组织主表，同时支持从业务库同步。这个设计非常合理，因为组织不仅服务查询过滤，还服务账号授权、树展示、默认组织选择等治理能力。如果直接在业务库组织表上耦合全部后台行为，后续治理会变得非常脆弱。

### 14.3 OrgService 的实现已经具备平台属性

OrgService 现在不仅能返回组织树，还能：

- 解析组织子树
- 返回组织路径
- 从业务库同步组织
- 清理相关缓存
- 获取组织下已授权用户

这说明组织系统已经不是“一个下拉框的数据来源”，而是整个平台权限边界的支柱。

### 14.4 UserServiceImpl 已具备基础账号治理能力

当前用户服务已支持：

- 创建账号
- 更新账号
- 启停账号
- 修改密码
- 分配组织权限
- 回收组织权限
- 解析用户可访问 org 列表

而且 MANAGER 与 ADMIN 的能力边界也被编码进了服务逻辑，而非仅仅写在文档里。

## 15. 认证、安全过滤链与请求上下文

### 15.1 TraceFilter 与 JwtAuthFilter 的配合是当前实现的一大亮点

请求进入系统后，TraceFilter 会优先建立 requestId 并写入 TraceContext。随后 JwtAuthFilter 再解析用户身份、角色和组织信息，并补充进同一个上下文对象。这样整个后续服务链都能拿到：

- requestId
- userId
- role
- orgId

这个设计使审计、日志、响应统一结构都能共享同一份上下文。

### 15.2 JWT 黑名单机制是实用且必要的

很多内部系统只做 JWT 签名校验，不做登出黑名单。Text2Report 当前已经通过 Redis blacklist 实现 token 失效控制，这使“退出登录后 token 仍可使用”的问题得到缓解，是一个实际有价值的增强。

### 15.3 SecurityConfig 的 URL 边界划分比较合理

当前访问控制大致分为：

- 登录与健康检查公开
- 查询端需登录
- 元数据、用户、组织、向量接口需更高角色
- 若干危险组织写接口直接 denyAll

这种策略说明后端并未把所有能力暴露在同一安全级别上。

## 16. 缓存、限流与审计：平台稳定性三件套

### 16.1 查询缓存实现是实际可用的

QueryCacheService 以“问题 + 组织范围”作为逻辑维度生成缓存键，并设置 TTL。这一做法在当前场景非常合适，因为同一问题在不同组织范围下的结果理应不同，而同一组织下的重复查询通常高度可缓存。

### 16.2 元数据变更会触发缓存失效

这一点很重要。系统在术语、示例、字段、JOIN、DDL 导入等元数据变更后，会显式清空查询缓存。否则缓存将把旧 Prompt 语义长期带入新查询，这是很多 NL2SQL 系统容易忽略的问题。

### 16.3 AuditService 已经形成基础审计闭环

当前审计记录覆盖：

- 查询开始
- 查询成功
- 查询失败
- 查询阻断
- 缓存命中
- 用户反馈

同时还做了：

- Prompt 敏感信息脱敏
- Prompt 截断
- 异步写入

这说明项目已经意识到审计不是简单记一条 question/sql，而是要面向追责和排障设计。

### 16.4 当前审计仍需继续扩展

虽然查询审计主链已经具备，但从工程治理角度看，后续还应进一步统一：

- 管理员操作审计
- 元数据变更审计
- embedding 同步操作审计
- 用户授权变更审计

部分表结构已经预留，但系统级运营视角的完整性还需要进一步验证。

## 17. RAG 与向量检索：M10 的真实价值

### 17.1 当前项目已经进入“可治理的 RAG”阶段

EmbeddingService 的存在意味着项目不再只依赖关键词匹配。它现在能够：

- 生成元数据 embedding
- 存储向量
- 做相似度搜索
- 提供全量同步能力
- 在元数据更新后异步补向量

这代表项目已经从传统 metadata search，升级为“语义检索增强的元数据装配”。

### 17.2 向量来源设计是正确的

当前 embedding 的来源不是业务事实数据，而是：

- SQL 示例
- 术语词典
- 表描述

这种设计与项目安全原则完全一致，也比“拿真实数据做 embedding”更适合企业内部合规场景。

### 17.3 管理端配套页面提升了可运维性

向量同步和检索测试页面的存在非常重要。因为 RAG 一旦出问题，最怕的是“后台完全不可观测，只能猜召回是否正常”。当前页面至少提供了：

- 向量数量统计
- 全量同步触发
- 检索测试入口

这已经让向量检索从“隐性算法能力”变成“可运维系统能力”。

## 18. 前端架构与交互实现

### 18.1 前端不是展示壳，而是完整的业务工作台

前端已经同时承担两类角色：

- 业务查询工作台
- 元数据与权限治理后台

这两个角色通过 QueryLayout 和 AdminLayout 分开，用户体验层面边界清晰，不会让普通查询用户进入后台治理路径。

### 18.2 路由体系与权限守卫简单但有效

通过 `AuthGuard` 和路由分组，前端能在视图层快速阻断不符合角色要求的访问。虽然真正安全依赖后端，但这个前端层约束可以避免大量无意义跳转和错误请求。

### 18.3 Zustand 方案适合当前规模

当前状态集中在：

- 认证态
- 组织选择
- 当前查询结果

这个规模下，Zustand 比 Redux 更轻，也足够稳定。当前还没有出现复杂并发数据依赖或缓存一致性问题，因此这一选型是合理的。

### 18.4 请求层实现质量较好

统一 Axios 实例做了几件对企业前端非常重要的事：

- 自动加 requestId
- 自动带 token
- 自动解包统一响应格式
- 401 自动清理认证状态
- 统一错误提示

这使页面层代码能保持相对干净。

### 18.5 查询页遵守了“前端不做业务推理”的原则

QueryPage 负责：

- 输入
- 调用 API
- 展示加载态、错误态
- 渲染摘要、图表和明细

它没有自行计算业务指标，也没有自行解释 SQL，符合系统定位。

### 18.6 管理页已经覆盖关键治理能力

当前管理页的范围相当完整，包括：

- DDL 上传解析
- 组织人员管理
- 账号管理
- 向量检索管理
- 表字段管理
- 术语词典管理
- JOIN 关系管理
- 示例管理
- 审计日志
- 数据源管理

这说明项目对“治理后台”是认真投入的，而不是停留在接口存在但没人能用的状态。

## 20. 测试、构建与工程一致性

### 20.1 测试覆盖不是空白，且覆盖方向正确

- 安全关键服务
- 编排服务
- 元数据服务

这说明团队把测试资源优先投给了高风险区域，而不是只给简单工具类补覆盖率。

### 20.2 当前工作区最需要修复的是“状态一致性”

比单个失败用例更重要的问题，是当前仓库对“当前状态”的叙述不一致：

- 状态文档说已全部通过
- 测试产物不支持这一结论

对资深工程团队来说，这类不一致会直接影响信任成本。因为任何准备进入真实环境验收的项目，首先要确保“仓库内的事实是一致的”。因此，下一步应做的不是解释，而是：

1. 清理旧测试产物
2. 重新执行测试
3. 将真实结果更新进状态文档

工程层面已具备：

- 多层分层结构
- 配置参数化
- Prompt 外置
- 测试基础
- 构建配置完整

但仍存在：

- 历史文档残留
- 构建产物留在仓库中带来的认知噪声
- 接口字段适配层偏多

这些问题都不是架构级错误，但它们会影响工程协作效率。

## 21. 当前实现中最值得肯定的部分

### 21.1 架构方向没有走偏

很多 NL2SQL 项目失败，不是因为模型不够强，而是因为一开始就把系统设计成“模型直连数据库”。Text2Report 没有走这条路，而是从一开始就强调：

- 元数据优先
- 接口抽象
- SQL Guard
- 只读执行
- 审计
- 权限

这是这个项目最大的优点。

### 21.2 治理后台是真实能力，不是装饰页面

DDL、术语、JOIN、示例、组织、用户、embedding 都已经形成后台页面和接口，这意味着系统的运行质量不必完全依赖开发改代码，而是可以部分转移到治理操作上。这是平台化的重要标志。

### 21.3 安全层投入是足够认真的

从 JWT 黑名单、AST 校验、只读数据源、权限前置、SQL 隐藏、审计脱敏这些细节可以看出，项目不是“事后补安全”，而是从实现层面认真处理了关键风险点。

## 22. 当前实现中最需要警惕的部分

### 22.1 文档、命名和真实代码的长期漂移

这类问题如果不及时处理，会在后续迭代中逐步恶化。最终效果通常不是“大家慢慢习惯”，而是：

- 新成员理解成本高
- 评审讨论时语义不统一
- 设计文档失去约束力

### 22.2 OrchestratorService 的继续膨胀风险

这是当前后端最需要提前治理的技术债。如果不拆分，未来每次改查询逻辑、修权限、补摘要、加策略，都会把复杂度继续压向一个类。

### 22.3 DDL 解析器的能力边界必须写清楚

当前方案适合 Demo 和受控输入，但不应让业务方误以为“任何 DDL 都能准确自动导入”。应在产品和文档层面明确它是受约束输入能力。

### 22.4 真实环境验收仍是决定项目质量的关键缺口

就当前代码而言，系统已经具备“看起来能跑通”的条件；但对企业系统来说，真正决定是否可靠的是：

- PostgreSQL
- Redis
- LLM provider
- Ollama embedding
- 向量库
- 权限链路
- 网络延迟与超时

这些都必须在真实环境中完成验证。仓库当前没有足够证据表明这一阶段已完成。

## 23. 下一阶段技术建议

### 23.1 第一优先级：统一事实

最先要做的不是加新功能，而是统一事实层：

1. 重新执行后端测试并清理旧 surefire 产物。

3. 收敛元数据库命名、文档命名与实现命名。

### 23.2 第二优先级：拆编排、稳边界

建议将查询编排拆解为更清晰的工作流组件，例如：

- 组织与权限解析器
- Metadata 检索与上下文构造器
- SQL 生成与修复工作流
- 结果装配器
- 审计与缓存协同器

这样可以在保留当前逻辑的基础上提升可维护性。

### 23.3 第三优先级：完成真实环境验收闭环

- 登录与权限生效
- 组织切换与组织过滤正确性
- 示例、术语、表描述检索效果
- embedding 全量同步耗时与成功率
- SQL Guard 对危险语句拦截验证
- 查询缓存命中与失效验证
- 审计记录完整性验证

### 23.4 第四优先级：继续提升语义质量

在治理基础稳定后，再逐步推进：

- 更强的意图识别
- 更严谨的图表推荐
- 示例覆盖面提升
- 术语词典规范化
- JOIN 图谱质量治理

注意顺序必须保持：先治理元数据，再提升模型智能度。

## 24. 总体结论

Text2Report 当前代码库已经具备一个企业级受控 NL2Report 系统应有的核心骨架。它不是聊天式 Demo，也不是把模型直接接到数据库上的危险原型，而是明确围绕元数据治理、权限边界、只读执行、AST 安全、审计留痕和 RAG 检索构建的系统。前后端结构完整，后端主链路闭合，治理后台能力也已经形成。

从资深开发人员视角看，这个项目最值得肯定的地方不是用了哪些技术，而是大方向基本正确：它把最难、最容易失控的部分提前制度化了，包括元数据先行、接口抽象、安全校验、运行时审计和组织权限前置。这使项目具备继续向稳定企业内测推进的现实基础。

同时，项目当前仍然处于“代码骨架成熟，但工程一致性和真实环境验收尚未完全收口”的阶段。最需要处理的不是推倒重来，而是把现有优势固化下来：统一文档与实现事实、修正状态不一致、拆分过重服务、完成真实环境验收。只要这几步执行到位，当前系统完全有机会从高质量 Demo 进入稳定可控的企业内部试运行阶段。
